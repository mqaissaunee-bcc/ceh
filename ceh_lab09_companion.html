Overview — what this lab is really teaching

Metasploit is the framework that organizes offensive security into a common structure: a catalog of modules, a database of what you've found, and a repeatable find → configure → run workflow. This lab is about learning that structure — not memorizing exploits — plus the Armitage GUI that sits on top of it. It supports the exploitation work in Module 6: System Hacking.

The mental model that makes everything else easy: every action in Metasploit is a module, and modules come in a few flavors — exploits, payloads, auxiliary (scanners, like WMAP), post, and encoders. Learn to search, use, set, and run any module and the 2,000+ others work the same way.

The environment you're working in

You run Metasploit from Kali against the intentionally vulnerable targets in the pod (the OWASP/Mutillidae web app and a Metasploitable-style host). The database stores hosts and services as you discover them, so later modules can draw on what earlier steps found.

Command walkthrough

Task 1 — Start the framework

1 Initialize the database and launch the console

root@kali:~# msfdb init
root@kali:~# msfconsole

msfdb init sets up the PostgreSQL database that lets Metasploit remember hosts, services, and loot; msfconsole drops you at the msf6 > prompt. Inside, db_status confirms the database is connected and help lists everything.

Task 2 — Scan a web app with the WMAP module

2 Load and run WMAP

msf6 > load wmap
msf6 > wmap_sites -a http://TARGET
msf6 > wmap_targets -t http://TARGET
msf6 > wmap_run -e

WMAP is an auxiliary module — a scanner, not an exploit. You register a site, point it at a target, and run the enabled checks. The findings land in the database, ready for the next step. It's a tidy example of the module workflow with nothing dangerous happening.

Task 3 — The find → configure workflow

3 Search, select, and inspect a module

msf6 > search type:exploit name:TERM
msf6 > use MODULE_PATH
msf6 > show options
msf6 > info

This is the loop you'll repeat forever: search to find a module, use to select it, show options to see the required settings (the ones marked yes you must fill in), set NAME value to configure them, and info to read what it does before you run anything. Configuring a module safely — reading info first — is the habit that separates a professional from a button-masher.

Task 4 — Armitage, the GUI

4 Visualize the same framework

Armitage is a graphical front-end to Metasploit: it draws hosts on a canvas, runs db_nmap scans, and exposes the same modules through menus. It's useful for seeing the structure at a glance.

Currency note — Armitage in 2026

Armitage is no longer actively maintained and isn't in current Kali by default; the modern graphical option for team engagements is Metasploit Pro or a C2 framework. Learn Armitage here to see the workflow, but expect to live in msfconsole in practice — the CLI is where the framework actually stays current.

Command reference — beyond the lab

Module types

TypeWhat it is
exploitCode that takes advantage of a specific vulnerability
payloadWhat runs after an exploit succeeds (e.g. a Meterpreter session)
auxiliaryScanners, fuzzers, and tools that don't exploit (WMAP lives here)
postPost-exploitation actions on an existing session
encoder / nopTransform payloads (historically for AV evasion)

Console essentials

The defender's view

Metasploit is a catalog of the already-known

Framework modules target published vulnerabilities. Almost everything it can do is stopped by doing the basics well.

  • Patch — a patched system has no exploit module to match. This is the single biggest defense.
  • Detect the signatures — IDS/IPS and EDR recognize common Metasploit payloads and exploit traffic; default encoders no longer evade modern defenses.
  • Reduce attack surface — fewer exposed services means fewer modules apply (the WMAP findings are your fix list).
  • Segment and least-privilege — limit what a single successful exploit can reach next.
  • Use it defensively — the same framework validates whether your patches and detections actually hold.

CEH v13 exam relevance

Framework fundamentals underpinning Module 6: System Hacking. High-yield facts:

  • Module types: exploit, payload, auxiliary, post, encoder — and what each is for.
  • The workflow: search → use → show options → set → run.
  • Payload families: staged vs. stageless, and bind vs. reverse connections.
  • Meterpreter as an in-memory post-exploitation payload.
  • msfconsole, msfdb, msfvenom and the role of the database.

Check yourself

1. WMAP is which type of module, and how do you know it won't exploit anything?

An auxiliary module — scanners and tools that gather information live there, as opposed to exploit modules that take advantage of a vulnerability.

2. Put the core workflow in order: set, use, show options, search, run.

search → use → show options → set → run.

3. What's the single most effective defense against most Metasploit exploit modules?

Patching — modules target published vulnerabilities, so a patched system has nothing for them to hit.

4. db_status reports disconnected. What did you skip?

Initializing/starting the database — run msfdb init (and ensure PostgreSQL is running) before launching the console.
