Overview — what this lab is really teaching

If you can read the packets on a wire, you can see passwords, files, and sessions that their owners assumed were private. This lab is the two-step rhythm every analyst uses: capture the traffic with tcpdump, then analyze it in Wireshark. It's Module 8: Sniffing.

The twist that makes it click: you'll generate your own SMB traffic with smbclient, capture it, and then go find it again in Wireshark. Seeing cleartext data you produced show up in a capture is the moment "use encryption" stops being a slogan.

The environment you're working in

You capture and analyze on Kali. The traffic you'll study is SMB (Windows file-sharing) to the OWASP BWA host at 192.168.68.12, generated on purpose with smbclient. Capture happens at the command line with tcpdump; the reading happens in the Wireshark GUI.

Command walkthrough

Read this before you copy anything

The source PDF hides two traps in these commands: the capture command shows an en-dash –s0 instead of a hyphen -s0, and the smbclient option uses curly quotes '…'. Both break at the shell. The copy buttons here emit clean characters.

Task 1 — Capture with tcpdump

1 Read the manual

root@kali:~# man tcpdump

tcpdump is the universal capture tool — no GUI, runs anywhere, writes standard files. Worth knowing even though Wireshark is prettier.

2 Start a capture to a file

root@kali:~# tcpdump -i eth0 -s 0 -w testdump.pcap

-i eth0 picks the interface, -s 0 sets the snap length to "capture the whole packet" (not just the headers), and -w testdump.pcap writes raw packets to a file you'll open in Wireshark. Leave it running; it captures until you stop it with Ctrl-C.

Why -s 0 matters

Older tcpdump truncated packets by default, cutting off payloads. -s 0 keeps the full packet so the data you're hunting for is actually in the file.

3 Generate traffic to capture

root@kali:~# smbclient -L 192.168.68.12 --option='client min protocol=NT1'
root@kali:~# smbclient \\\\192.168.68.12\\owaspbwa --option='client min protocol=NT1'

In a second terminal, -L lists the shares on the host, then you connect to the owaspbwa share. --option='client min protocol=NT1' forces the ancient SMBv1 dialect, which is unencrypted — exactly what makes the traffic readable in the next step. Inside the smb:\> prompt you can run ls, help, and exit.

Task 2 — Analyze with Wireshark

4 Stop the capture and open it

root@kali:~# wireshark

Stop tcpdump (Ctrl-C), launch Wireshark, and open testdump.pcap. Now filter to just the traffic you care about — type smb or smb2 in the display filter bar — and use right-click → Follow → TCP Stream on a packet to reassemble the whole conversation into readable text.

📸 Screenshot for your report

Capture Wireshark filtered to smb, and a Follow-TCP-Stream view showing the share name or other cleartext from your session.

The whole point in one view

Follow TCP Stream turns a pile of packets back into the conversation. On an unencrypted protocol, that conversation is plain text — share names, filenames, sometimes credentials.

Capture filters (tcpdump/BPF syntax) decide what gets recorded; display filters (Wireshark syntax) decide what you see in a file you already have. Don't mix the two grammars.

The defender's view

Sniffing cuts both ways

The same capture that hands an attacker cleartext credentials is the analyst's primary tool for detecting intrusions. The lesson is less "sniffing is bad" and more "unencrypted protocols are indefensible."

  • Encrypt everything in transit — SMB signing/encryption, HTTPS, SSH. A sniffer on an encrypted link gets ciphertext.
  • Kill legacy protocols — SMBv1, Telnet, FTP, plain LDAP. If the lab had to force SMBv1, that tells you it should be off.
  • Segment and control the switch — port security, DHCP snooping, and dynamic ARP inspection make it harder to get into a position to sniff (see Lab 12).
  • Use capture defensively — the same Wireshark/tcpdump skills power intrusion detection and incident response.

Check yourself

1. What does -s 0 do in the tcpdump command, and why does it matter here?

It sets the snap length to capture the entire packet, not just headers — so the payload you're hunting for (share names, cleartext) is actually saved in the file.

2. Why does the lab force client min protocol=NT1 (SMBv1)?

SMBv1 is unencrypted, so the conversation is readable in Wireshark. It also demonstrates why the obsolete dialect should be disabled in the real world.

3. You opened a huge capture. What two Wireshark moves get you to the useful part fastest?

Apply a display filter (e.g. smb), then right-click a packet and Follow → TCP Stream to reassemble the conversation.

4. What's the difference between a capture filter and a display filter?

A capture filter (BPF syntax) limits what gets recorded; a display filter (Wireshark syntax) limits what you see in an already-captured file. Different grammars.

Cheat sheet

Capture (tcpdump)

  • tcpdump -i eth0 -s 0 -w out.pcap
  • tcpdump -i any -nn port 445
  • tcpdump -r out.pcap -A — read + ASCII
  • Ctrl-C to stop
  • Generate: smbclient -L HOST --option='client min protocol=NT1'

Analyze (Wireshark)

  • Filter: smb · http · dns
  • ip.addr == HOST · tcp.port == 445
  • Right-click → Follow → TCP Stream
  • Statistics → Conversations / Protocol Hierarchy
  • File → Export Objects — pull files out of a capture
