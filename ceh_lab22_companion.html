Overview — what this lab is really teaching

Windows keeps its local account password hashes in the SAM (Security Account Manager). This lab shows how those hashes can be pulled offline — with access to the files rather than a login — and then cracked. It's the Windows counterpart to Lab 08 and part of Module 6: System Hacking.

Two ideas carry the lab. First, the SAM is encrypted with a key (the bootkey / SYSKEY) stored in the SYSTEM hive — so you need both files, not just the SAM. Second, the difference between LM and NTLM hashes is the difference between "cracked in seconds" and "actually hard" — which is the whole defensive story.

The environment you're working in

You use FTK Imager on Windows to locate and export the SAM and SYSTEM files (they're locked while Windows is running, which is why a forensic tool or offline access is needed), then move to Kali to extract and crack the hashes. The hand-off between the two machines is the realistic part: offline credential attacks almost always start with getting at the files some other way.

Command walkthrough

Task 1 — Locate the files with FTK Imager (Windows)

1 Find SAM and SYSTEM

FTK Imager can read a live or imaged file system and reach files Windows keeps locked. Navigate to C:\Windows\System32\config and export both SAM and SYSTEM. You need the pair — the SAM alone is useless without the SYSTEM hive's key.

Task 2 — Get the files onto Kali

2 Mount the share and copy

root@kali:~# mkdir Desktop/share
root@kali:~# sudo mount -t cifs -v -o user=Administrator,password=PASSWORD,vers=2.1 //HOST/share Desktop/share
root@kali:~# cp -a Desktop/share/. Desktop/Lab22

mount -t cifs attaches the Windows share so you can copy the exported files over. (vers=2.1 pins the SMB dialect so the mount negotiates cleanly; supply the share's own credentials in place of PASSWORD.)

Task 3 — Extract and crack

3 Pull the hashes with samdump2

root@kali:~# samdump2 Desktop/Lab22/system Desktop/Lab22/sam -o Desktop/Lab22/hash.txt

samdump2 takes the SYSTEM hive (for the bootkey) and the SAM (for the encrypted hashes) and writes the decrypted account hashes to a file. Giving it only one of the two is the classic mistake — it needs both.

📸 Screenshot for your report

Capture the samdump2 output showing the extracted account hashes (usernames and hash values).

4 Crack with John

root@kali:~# john --format=LM --wordlist=/usr/share/john/password.lst Desktop/Lab22/hash.txt

Forcing --format=LM cracks the weak LM portion. LM is almost comically breakable: it uppercases the password, splits it into two 7-character halves, and hashes each independently with DES — so a 14-character password is really just two short ones. If LM is present, it usually falls fast. For the stronger hash you'd use --format=NT instead. (See Lab 08 for the full cracking workflow.)

The defender's view

Offline hash theft is a physical-and-privilege problem

This attack needs access to the files, which means admin rights, physical access, or a stolen disk. Defend the files, and defend what a stolen hash is worth.

  • Encrypt the disk — BitLocker (with a TPM/PIN) makes the SAM and SYSTEM unreadable from offline access or a stolen drive.
  • Don't store LM hashes — off by default on modern Windows; confirm the policy stays that way.
  • Strong, unique passwords — the only thing that makes a dumped NTLM hash useless. Unique per host stops pass-the-hash from spreading.
  • Limit local admin and protect LSASS — Credential Guard and attack-surface-reduction rules keep credentials out of reach even on a running box.
  • Physical security — the oldest control still matters: an attacker who can boot from media can read an unencrypted disk.

CEH v13 exam relevance

Windows credential storage within Module 6: System Hacking. High-yield facts:

  • SAM stores local hashes; the SYSTEM hive holds the bootkey needed to decrypt it.
  • LM vs. NTLM — why LM is trivially weak (uppercase, 7-char DES halves, no salt).
  • Neither is salted → vulnerable to rainbow tables and pass-the-hash.
  • Offline vs. online attacks, and why offline needs file access.
  • Tools: samdump2, pwdump, Impacket secretsdump, John/Hashcat.
  • Defenses: disable LM, BitLocker, Credential Guard, strong unique passwords.

Check yourself

1. Why do you need the SYSTEM hive as well as the SAM?

The SAM is encrypted with the bootkey/SYSKEY, which is stored in the SYSTEM hive. Without SYSTEM you can't decrypt the hashes.

2. Give two reasons LM hashes are so weak.

Any two: the password is uppercased (shrinking the keyspace); it's split into two independent 7-character halves; it's unsalted DES. Together these make it trivially crackable.

3. Which single control makes an offline SAM attack moot even if the disk is stolen?

Full-disk encryption (BitLocker) — the SAM and SYSTEM files can't be read without the key.

4. Why does using a unique password per host limit the damage of a dumped hash?

An unsalted NTLM hash can be reused in a pass-the-hash attack. If each host's local password is unique, one stolen hash doesn't unlock the others.

Cheat sheet

Extract

  • Get both SAM + SYSTEM (FTK Imager / offline)
  • mount -t cifs -o user=,password= //HOST/share dir
  • samdump2 SYSTEM SAM -o hash.txt
  • Modern: secretsdump.py -sam SAM -system SYSTEM LOCAL

Crack & defend

  • john --format=LM hash.txt
  • john --format=NT hash.txt
  • Defend: BitLocker, no LM, Credential Guard
  • strong unique passwords (stops pass-the-hash)
