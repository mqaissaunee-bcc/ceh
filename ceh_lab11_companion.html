Overview — what this lab is really teaching

Most of this course attacks servers. Client-side exploitation flips the target to the user and their browser — because a patched server behind a firewall is often harder to reach than the person who clicks a link. This lab uses BeEF (the Browser Exploitation Framework) to "hook" a browser and then operate against it. It maps to Module 7: Malware Threats and the client-side attack surface.

The concept: if you can get a victim's browser to load a small piece of JavaScript (the hook), that browser checks in with your BeEF server and becomes a foothold — you can fingerprint it, show convincing fake prompts, and launch further modules. The defense follows directly: don't let untrusted scripts run, and keep the browser patched.

The environment you're working in

You run the BeEF server on Kali and browse to a page carrying its hook from a victim machine in the pod. BeEF's control panel (a web UI) then lists every hooked browser and the modules you can run against it. Everything stays inside the lab network.

Walkthrough

Task 1 — Hook a browser

1 Start BeEF and hook a browser

root@kali:~# beef

Launch BeEF (it runs in a Docker container and takes 1–2 minutes to come up) and log into its control panel with beef / password. BeEF serves a hook (hook.js); any browser that loads a page containing it becomes hooked. The lab demonstrates this with its built-in demo: from the OpenSUSE VM (login osboxes / osboxes.org), open Firefox and browse to 192.168.9.2:3000/demos/basic.html. Getting that script in front of a real victim would be the social-engineering step (Lab 18) or an XSS flaw (Lab 24).

Screenshot for your report

Capture the BeEF panel with the hooked browser (192.168.9.1) appearing under "Online Browsers".

2 See what the hook reveals

Back on Kali, select the hooked browser (192.168.9.1) and read its details — the Browser UA String shows it's Firefox 43, along with OS and plugins. That inventory is reconnaissance: it tells the attacker which client-side weaknesses apply. Then generate an event: on the victim, type secret into the demo's "Insert your secret here" field, refresh BeEF (F5), and open the Logs tab — BeEF has captured the keystrokes.

Screenshot for your report

Capture the Logs tab showing the captured keystrokes from the hooked browser.

Task 2 — Run client-side modules

3 Operate against the browser

Open the Commands tab and the Module Tree. Modules are color-coded for the current browser: green = should work, orange = may not work, red = won't work. The lab runs several: Detect Toolbars and Fingerprint Browser (PoC) from Browser inventory, then Fake Notification Bar (Firefox) under Social Engineering — select a module, click Execute, and read the entry in the Module Results History.

The social-engineering payoff

Fake Notification Bar shows the victim a convincing "install a plug-in" prompt. The lab then drives them to a fake order form (the "BeEF-Hamper"), where typed details — name, address, even a card number — are captured back in BeEF's Logs. A hooked browser is a position inside the user's session, often behind the firewall, from which to phish, map the network, or pivot.

Reference — beyond the lab

How the hook gets delivered

VectorHow the script loads
Social engineeringA link to an attacker page (Lab 18)
Stored / reflected XSSInjected into a trusted site (Lab 24)
MiTM injectionAdded to HTTP responses in transit (Lab 12)
Malvertising / compromised siteServed from a third-party resource

Related client-side avenues: malicious documents and macros, browser/plugin exploits, and framework tools like Metasploit's browser modules.

Where people get stuck

SymptomCauseFix
Browser never appears as hookedThe page didn't actually load hook.jsConfirm the hook URL/IP is correct and reachable from the victim.
Hook drops offlineVictim navigated away or closed the tabThe hook lives only while the page is open — keep the tab active.
Can't reach the BeEF panelService not started / wrong portStart BeEF and use the control-panel URL it prints on launch.
Modules do nothingModern browser blocks the techniqueExpected — current browsers mitigate many old client-side tricks.

The defender's view

Cut off the script, patch the browser, teach the user

The hook is just JavaScript from somewhere it shouldn't be. Stop that and the attack has nowhere to stand.

  • Content Security Policy (CSP) — restrict which scripts a page may load, so an injected hook is refused.
  • Fix XSS at the source — output encoding and input validation keep attacker script off trusted pages (Lab 24).
  • Patch browsers and plugins — removes the client-side exploits that follow a hook.
  • User awareness — the delivery is usually a link or a convincing prompt; trained users don't click or type.
  • Encrypt traffic & filter web — HTTPS blocks MiTM hook injection; web filtering blocks known-malicious hosts; EDR and browser isolation add backstops.

CEH v13 exam relevance

Client-side and malware-delivery concepts in Module 7: Malware Threats (with ties to social engineering and web). High-yield facts:

  • Client-side vs. server-side attacks — targeting the user/browser instead of the server.
  • BeEF and the browser-hooking concept.
  • Delivery via social engineering, XSS, and MiTM injection.
  • Defenses: CSP, patching, awareness, output encoding, web filtering.
  • How a hooked client becomes a pivot behind the perimeter.

Check yourself

1. What does it mean for a browser to be "hooked" in BeEF?

The browser has loaded BeEF's hook.js, so it periodically checks in with the BeEF server and can be issued commands — a foothold inside the user's session.

2. Name two ways the hook script could reach a victim's browser.

Any two: a social-engineering link to an attacker page, a stored/reflected XSS flaw on a trusted site, MiTM injection into HTTP, or a compromised/third-party resource.

3. Why is a hooked browser dangerous even when the server perimeter is well defended?

It's a position inside the user's session and often behind the firewall, from which an attacker can phish, map the internal network, or pivot.

4. Which server-side control refuses an injected hook from loading?

A Content Security Policy (CSP) that restricts which script sources the page is allowed to load.
