Overview — what this lab is really teaching

A buffer overflow is what happens when a program writes more data into a fixed-size buffer than it can hold, spilling into whatever memory sits next to it. This lab doesn't attack anything — you write your own tiny vulnerable program, watch it misbehave, then fix it. That's the clearest way to understand a bug class that has caused decades of real-world compromises. It underpins the exploitation content in Module 6: System Hacking (and web-server flaws in Module 13).

The goal here is understanding, not exploitation. Once you've seen why C happily writes past the end of an array, both the vulnerability and every mitigation that exists to stop it make immediate sense.

The environment you're working in

Everything is local on Kali: a text editor, the gcc compiler, and a terminal. You compile and run a small program you wrote yourself — nothing leaves the machine, and there's no target but your own code.

Walkthrough

Read this before you copy anything

The compile commands in the source PDF use an en-dash (–o) instead of a hyphen (-o). Paste it and gcc complains. Retype the hyphen, or use the copy buttons.

Task 1 — Write a vulnerable program

1 The vulnerable pattern

The program declares a small fixed buffer — say room for 8 integers — then reads however many values the user asks to enter, with no check that the count fits:

// the vulnerable shape (illustrative)
int buffer[8];
int n;  scanf("%d", &n);           // user says how many
for (int i = 0; i < n; i++)         // no bound on n!
    scanf("%d", &buffer[i]);        // writes past buffer when n > 8

The bug is the missing comparison between n and the buffer's size. C does no bounds checking of its own, so the loop will cheerfully write a 9th, 10th, 100th value into memory it was never given.

Task 2 — Watch it overflow

2 Compile and run

root@kali:~# gcc vuln1.c -o vuln1
root@kali:~# ./vuln1

When the program asks how many integers to enter, give it 9 — one more than the buffer holds. That 9th value lands outside the buffer, corrupting whatever was adjacent on the stack. Depending on what you clobber, you'll see garbage output or a segmentation fault (the OS killing the program for touching memory it shouldn't).

Why this is the whole point

The memory next to a local buffer includes bookkeeping the program relies on — in a real exploit, the prize is the saved return address. Overwrite it and you can redirect where the program jumps next. The toy program only crashes; the mechanism is identical to the serious ones.

Task 3 — Fix it

3 Add the bounds check

// the fix: refuse anything that won't fit
if (n < 0 || n > 8) { printf("too many\n"); return 1; }
root@kali:~# gcc fixed_vuln1.c -o fixed_vuln1
root@kali:~# ./fixed_vuln1

The fixed version checks the count against the buffer's capacity before writing. Enter 9 now and it refuses instead of corrupting memory. One comparison is the entire difference between a vulnerability and safe code.

Reference — beyond the lab

The stack, roughly

A function's local variables, saved frame pointer, and saved return address live together on the stack. A buffer that overflows writes toward those saved values — which is why overwriting the return address is the classic exploitation goal, and why the mitigations below exist to protect exactly that region.

The defender's view

This whole class of bug is preventable

Buffer overflows are a coding problem with well-known engineering answers. Defense is mostly "write it right, then let the compiler and OS back you up."

  • Validate lengths — bounds-check every write into a fixed buffer, as the fix shows.
  • Use safe functions — the bounded versions in the table; avoid gets entirely.
  • Prefer memory-safe languages — Rust, Go, Java, Python don't expose this foot-gun for ordinary code.
  • Turn on the protections — stack canaries, ASLR, DEP/NX, FORTIFY are on by default in modern toolchains; keep them on.
  • Patch — real overflows in shipped software become CVEs; patching closes them before they're exploited.

CEH v13 exam relevance

Foundational memory-corruption concept behind much of Module 6 and server-side exploitation. High-yield facts:

  • What an overflow is — writing beyond a buffer's bounds into adjacent memory.
  • Stack vs. heap overflows, and the role of the saved return address.
  • Overwriting the return address → redirecting execution → potential code execution.
  • Dangerous functions (gets, strcpy) and their safe replacements.
  • Mitigations: stack canaries, ASLR, DEP/NX — know what each stops.
  • Why C/C++ are affected and memory-safe languages mostly aren't.

Check yourself

1. In the vulnerable program, exactly what is missing that causes the overflow?

A bounds check — nothing compares the requested count against the buffer's size before writing, so the loop writes past the end.

2. Why is overwriting the saved return address the classic exploitation goal?

The return address controls where the program jumps when the function finishes. Overwriting it lets an attacker redirect execution, potentially to code of their choosing.

3. What does a stack canary do?

It places a known guard value just before the return address; if an overflow changes it, the program detects the tampering and aborts before returning.

4. Your program overflows but doesn't crash. Does that mean it's safe?

No. Overflow is undefined behavior — it may silently corrupt memory without crashing, which is actually more dangerous than an obvious segfault.
