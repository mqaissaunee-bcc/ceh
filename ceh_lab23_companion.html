Overview — what this lab is really teaching

The last phase of an intrusion is covering tracks: hiding data and destroying the evidence of what happened. This lab shows both halves — hiding files in NTFS alternate data streams and Linux extended attributes, and wiping logs and command history. It completes the methodology in Module 6: System Hacking.

For a defender, this is one of the most valuable labs in the set — not because you'll clear logs, but because knowing how attackers hide and erase tells you exactly what to protect, and because the act of clearing logs is itself a detectable event. Anti-forensics is the mirror image of forensics.

The environment you're working in

You work across Windows (NTFS streams, ADS Spy, OpenStego) and Kali/Linux (extended attributes and log files). Every command touches files and logs on the practice machines only.

Command walkthrough

Read this before you copy anything

The setfattr values in the source PDF are wrapped in curly quotes, which the shell won't parse — use straight quotes (the copy buttons here do).

Task 1 — Hiding data (Windows NTFS streams)

1 Alternate Data Streams

NTFS lets a file carry hidden alternate data streams — extra content attached to a file that doesn't show in a normal directory listing or change the visible size. The lab hides data in a stream, then uses ADS Spy to locate it and OpenStego to pull steganographically-hidden content back out. The lesson: a clean-looking file can carry a payload.

Task 2 — Hiding data (Linux extended attributes)

2 Stash data in xattrs

root@kali:~# touch lab23.txt
root@kali:~# setfattr -n user.attribute1 -v 'data hidden here' lab23.txt
root@kali:~# setfattr -n user.attribute2 -v 'data also hidden here' lab23.txt
root@kali:~# getfattr -d lab23.txt

Create a file, then setfattr attaches named extended attributes to it (the lab adds two) — metadata that ordinary tools like cat and ls don't display. getfattr -d dumps them back. It's the Linux analogue of NTFS streams: data riding invisibly alongside a file.

attr may not be installed

The setfattr/getfattr tools come from the attr package, which isn't present on every distro. On Debian/Ubuntu/Kali: sudo apt install attr.

Task 3 — Destroying evidence (Linux logs)

3 Make some activity, then find it in the logs

root@kali:~# sudo ifconfig
root@kali:~# sudo grep sudo /var/log/auth.log
root@kali:~# cat /var/log/auth.log

Running a sudo command writes an entry to /var/log/auth.log; grep sudo pulls out those entries so you can see the trail you just left. last -f reads the login records in wtmp (successful) and btmp (failed).

root@kali:~# last -f /var/log/wtmp
root@kali:~# last -f /var/log/btmp

4 Wipe the logs and the shell history

root@kali:~# cat /dev/null > /var/log/auth.log
root@kali:~# cat /dev/null > /var/log/wtmp
root@kali:~# cat /dev/null > /var/log/btmp
root@kali:~# ls -al
root@kali:~# cat .bash_history
root@kali:~# > .bash_history
root@kali:~# cat .bash_history

cat /dev/null > file truncates a log to empty (run last again and the records are gone). Then ls -al reveals the hidden .bash_history (every user has one), cat shows the commands it recorded, > .bash_history empties it, and the final cat verifies it's clear. This is the "erase the camera footage" step.

But notice what you can't undo

On a properly run network these logs were already shipped off the machine the moment they were written. Clearing the local copy changes nothing on the log server — and the clearing itself is logged. That's the point of the whole lab.

The defender's view

Win this phase before it happens

Covering tracks only works on evidence the attacker can reach. Move the evidence out of reach and make tampering noisy.

  • Centralized / remote logging — ship logs to a SIEM or syslog server in real time. Clearing the local copy is then pointless; the record is already elsewhere.
  • Tamper-evident, append-only logs — write-once storage and integrity hashing so alterations are detectable.
  • Alert on the clearing itself — log truncation, history wipes, and Windows Event ID 1102 (log cleared) are high-fidelity indicators of compromise.
  • File integrity monitoring — tools like AIDE/Tripwire flag hidden streams, xattr changes, and timestomping.
  • Least privilege — if the attacker never reaches root/SYSTEM, they can't touch the logs in the first place.

Check yourself

1. Why does clearing local logs often fail against a well-run network?

Logs are shipped to a central/remote log server as they're generated, so the attacker's copy isn't the only one. The off-box record survives.

2. What's an NTFS alternate data stream, and why is it useful for hiding data?

Extra content attached to an NTFS file that doesn't appear in normal directory listings or change the visible size — so data can ride hidden alongside an innocent-looking file.

3. Why do attackers truncate a log rather than delete the file?

A missing log file is conspicuous; an empty-but-present file is less obviously tampered with (though both are detectable).

4. Name one way the act of clearing logs is itself detected.

Windows Event ID 1102 ("audit log was cleared"), auditd rules on log files, or a SIEM alert when a remote log source suddenly goes silent/empties.

Cheat sheet

Hide & wipe

  • NTFS ADS (Windows) — find with ADS Spy
  • setfattr -n user.x -v 'data' file
  • getfattr -d file
  • cat /dev/null > /var/log/wtmp
  • > .bash_history · Windows: clearev

Defend

  • Central/remote logging (SIEM)
  • Append-only / tamper-evident logs
  • Alert on log clearing (Event ID 1102)
  • File integrity monitoring (AIDE/Tripwire)
  • Least privilege
