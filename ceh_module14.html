CEH v13 Module 14: Hacking Web Applications

Hacking Web Applications

The application layer and its vast attack surface: the OWASP Top 10 (2025), injection and cross-site scripting, broken access control and authentication flaws, file upload and API weaknesses, the DAST tooling that finds them, and the secure coding that prevents them.

🕸️ Overview

The largest attack surface in the course

Module 13 secured the web server — the platform. This module attacks what runs on top of it: the web application itself, with its custom code, input handling, authentication, and business logic. This is the single largest and most varied attack surface an ethical hacker faces, and for a simple reason: every web application is uniquely written. A web server is a known product with known vulnerabilities you can look up; a web application is bespoke software, and its flaws are as varied as the developers who wrote it. There is no patch for a logic flaw in a shopping cart or an authorization mistake in an API — each must be found and fixed individually.

Web applications are also where the value lives. They handle logins, personal data, payments, and business operations, sitting directly on top of the databases and services an attacker ultimately wants. Combined with their universal internet exposure, this makes them the most common target of real-world attacks — and the reason CEH devotes an entire module to the methodology of testing them.

Keeping the layers straight

This module is the middle of a three-part web cluster, and the boundaries matter. Module 13 covered the server — Apache, Nginx, IIS, and their configuration. This module covers the application — the code and logic running on that server. Module 15 takes one especially important application vulnerability, SQL injection, and treats it in dedicated depth. So while injection in general is covered here, the deep dive into SQLi is deferred to the next module, just as this module was deferred from the last. Holding this map in mind tells you which techniques apply to a given weakness: a server misconfiguration is Module 13, an authorization flaw in the app is Module 14, and a database-injection flaw gets its full treatment in Module 15.

The organizing framework: OWASP

Web application security is vast, so the field relies on a shared framework to organize it: the OWASP Top 10, the security industry's most widely-cited standard, produced by the Open Web Application Security Project. It ranks the most critical categories of web application risk based on real-world data, and it is the backbone of this module. Crucially, it is a living standard — the current edition is 2025, released in November of that year, which reshuffled the rankings and added new categories reflecting how modern applications are built and attacked. We'll work through it in the OWASP section, then dive into the specific attacks it names. Anyone serious about web application security learns to think in terms of the Top 10.

What this module covers

We start with architecture and methodology — how web applications are structured and the systematic process for testing them. Then the OWASP Top 10 (2025) as the organizing map of risk. From there we go deep on the most important attack families: injection and cross-site scripting (the classic code-into-data attacks), and broken access control and authentication (the #1 risk plus its close relatives — session flaws, IDOR, file upload, and API weaknesses). We survey the tools of web application testing — Burp Suite and OWASP ZAP chief among them — and close with countermeasures centered on secure coding, input validation, and defense in depth. Throughout, the emphasis is the tester's dual role: find these flaws under authorization, and help developers build applications that don't have them.

The exposure is not an invitation. Web applications are reachable by anyone, which makes it tempting to probe any site you can load — but testing an application you don't own, without written permission, is illegal regardless of how easy it is. These techniques are for authorized engagements and deliberately-vulnerable practice targets (DVWA, OWASP Juice Shop, WebGoat, and the labs on TryHackMe and Hack The Box), which exist precisely so you can learn them safely.

🏗️ Architecture & Methodology

How a web application is built

To find flaws in a web application, you first need a model of how one is put together, because each part is a place where things can go wrong. A modern web application is a multi-tier system. The client tier (the browser) runs HTML, CSS, and JavaScript — increasingly a rich single-page application (SPA) that does substantial work itself. The application tier (the server-side code, in PHP, Java, .NET, Python, Node.js) contains the business logic, handles authentication, and processes input. The data tier (databases and other stores) holds the persistent data. Between them flows a stream of HTTP requests and responses, and increasingly, communication happens through APIs — structured endpoints (often REST or GraphQL) that the front-end and third parties call directly.

Every tier and boundary is an attack surface. Client-side code can be manipulated because the attacker controls the browser. The application tier can be tricked into mishandling input or authorization. The data tier can be reached through injection. And APIs, which expose application functionality directly, have become one of the most attacked surfaces of all — modern apps are increasingly API-driven, and API parameter inputs are frequently under-tested, which is exactly where much injection and access-control risk now lives.

The core principle: never trust the client

One idea underlies nearly every web application vulnerability and defense, and it's worth stating plainly before anything else: the client cannot be trusted. The attacker controls their own browser completely — they can modify any request before it's sent, bypass any client-side validation, forge any header, and call any API endpoint directly. Every input arriving at the server, no matter how constrained it appeared in the browser, may have been tampered with. Security controls that live only in the client-side JavaScript — a disabled button, a hidden field, a length check — are not security at all, because the attacker simply removes them. This is why all real security decisions must happen on the server, and why "the app trusted input it shouldn't have" is the story behind most of the OWASP Top 10.

The testing methodology

Assessing a web application follows a systematic progression, mirroring the broader hacking methodology narrowed to this target.

1. Map
Crawl & understand
→
2. Analyze
Find entry points
→
3. Test
Probe for flaws
→
4. Exploit
Confirm impact

It begins with mapping — crawling and exploring the application to understand its pages, functions, and technologies, building a picture of everything it does. Next, analyzing the attack surface — cataloging every point where the application accepts input: URL parameters, form fields, headers, cookies, file uploads, and API endpoints, since each is a candidate for attack. Then testing — systematically probing those inputs for the vulnerability classes in the OWASP Top 10, watching how the application responds to unexpected or malicious input. Finally, exploitation — confirming a suspected flaw is real and demonstrating its impact, which turns a theoretical finding into a proven risk the organization must fix.

Manual skill, tool assistance

A defining feature of web application testing — one that distinguishes it from, say, network scanning — is how much it depends on human judgment. Automated scanners are essential for coverage and for catching known patterns, but many of the most serious flaws, especially broken access control and business-logic errors, are contextual: a tool cannot easily determine whether User A should be able to reach Record B, because only the application's intended business rules define that. This is why web application assessment blends automated scanning with skilled manual testing, and why the tester's understanding of how applications work — the subject of the rest of this module — matters more here than raw tool proficiency. With the architecture and process established, the OWASP Top 10 gives us the map of what to look for.

🔟 The OWASP Top 10

The industry's shared map of risk

The OWASP Top 10 is the most widely-cited web application security standard in the world — a ranked list of the ten most critical categories of web application risk, compiled by the Open Web Application Security Project from real-world testing data, reported CVEs, and community input. It is not a checklist of every possible bug, nor a compliance standard; it is a high-level grouping of the failure classes that break real applications most often, and it gives security professionals a shared vocabulary. It is updated periodically, and the current edition — 2025, unveiled at OWASP's Global AppSec conference in November 2025 — reflects how modern applications are built and attacked. Using the current list matters: an assessment framed around an outdated Top 10 misses the shifts the update was made to capture.

The OWASP Top 10 (2025)

The 2025 edition, in ranked order:

A01 · Broken Access Control

Still #1. Failures to enforce what users are permitted to do — accessing others' data, privilege escalation. Now absorbs SSRF and explicitly covers API authorization failures (BOLA/BFLA).

A02 · Security Misconfiguration

Up sharply from #5. Insecure defaults, overly permissive settings, and inconsistent controls — now so common that essentially all tested applications show some form of it.

A03 · Software Supply Chain Failures

New/expanded. Compromises across the ecosystem of dependencies, build systems, and distribution — a broadening of the old "vulnerable components," reflecting modern deployment.

A04 · Cryptographic Failures

Weak or missing cryptography that exposes sensitive data — poor algorithms, bad key handling, unencrypted data in transit or at rest.

A05 · Injection

Down from #3 but still critical. Untrusted data sent to an interpreter — SQL injection, XSS, command injection, LDAP/NoSQL injection. The one category defined by symptom rather than root cause.

A06 · Insecure Design

Architectural and design-level flaws — missing security controls by design, not implementation bugs. Fixed by threat modeling early, not patching late.

A07 · Authentication Failures

Broken authentication and session management — weak passwords, credential stuffing, flawed MFA, poor session handling.

A08 · Software or Data Integrity Failures

Trust and verification failures — insecure deserialization, tampered updates, compromised CI/CD pipelines.

A09 · Security Logging & Alerting Failures

Insufficient visibility into attacks. Renamed for 2025 to stress that logging without alerting has little value — you must be able to act in time.

A10 · Mishandling of Exceptional Conditions

New for 2025. Improper error handling, logic errors, and "failing open" — abnormal conditions that leak information or create exploitable states.

What the 2025 changes tell us

The shifts in the 2025 edition are worth reading as a story about how the field is changing. Broken Access Control holding #1 — and expanding to absorb SSRF and API authorization — confirms that access control is the hardest problem in web security, because it is inherently contextual: no tool can know your business rules. Security Misconfiguration leaping to #2 reflects the reality that teams deploy continuously but scan intermittently, leaving exposure windows. And the two new categories — Software Supply Chain Failures and Mishandling of Exceptional Conditions — mark the field's shift from isolated coding bugs toward the security of the entire software ecosystem and lifecycle. The overall trend is away from symptoms and toward root causes, with Injection the last remaining "symptom" category precisely because its many causes resist a single label.

How this maps to the rest of the module

The Top 10 organizes everything that follows. The next section takes Injection (A05) — including XSS and command injection — in technical depth (with SQL injection deferred to its own module). The section after covers Broken Access Control (A01) and Authentication Failures (A07), the access-and-identity failures that top the list, along with file upload and API weaknesses. Several categories connect to other modules: cryptographic failures to the cryptography module, misconfiguration back to Module 13's server hardening, and logging failures to the detection themes from the evasion module. The Top 10 is not just a list to memorize — it's the framework that tells a tester what to look for and a defender what to prioritize.

💉 Injection & XSS

The oldest and most dangerous idea in web security

Injection (OWASP A05) is the class of flaw where an application sends untrusted data to an interpreter as part of a command or query — and the interpreter, unable to tell the attacker's data from the developer's code, executes it. That single sentence captures a whole family of attacks: SQL injection, cross-site scripting, command injection, LDAP and NoSQL injection, and more. They differ only in which interpreter is targeted (a database, a browser, an OS shell), but they share one root cause: the failure to keep code and data separate. Understand that root cause and every injection variant becomes recognizable as the same mistake wearing different clothes.

Cross-Site Scripting (XSS)

Cross-Site Scripting injects malicious JavaScript into a web page so that it executes in the browsers of other users who view it. The attacker's target is not the server but the application's other users — the injected script runs with the victim's session and can steal their session cookie (tying directly to the session-hijacking module), harvest credentials, or take actions as the victim. XSS comes in three forms:

💾 Stored XSS

The malicious script is saved on the server (in a comment, profile, or message) and served to every user who views that content. The most dangerous form, because it attacks everyone automatically.

🪞 Reflected XSS

The script is reflected off a request — embedded in a crafted URL or form, echoed back in the response, and executed. Requires luring the victim into clicking the malicious link.

🌐 DOM-based XSS

The flaw is entirely client-side: vulnerable JavaScript manipulates the page's DOM using attacker-controlled input without the server ever being involved. Increasingly common in complex single-page apps.

A simple reflected example: if a search page echoes your query into the results without encoding it, submitting <script>alert(document.cookie)</script> causes that script to run in the browser. The defense is context-appropriate output encoding — ensuring that user data is rendered as inert text, never as executable markup — reinforced by a Content-Security-Policy and the HttpOnly cookie flag from Module 11.

Command injection

Command injection targets the operating-system shell. When an application passes user input to a system command without sanitizing it, an attacker can append their own commands and have the server execute them. If a diagnostic feature runs ping <user-input>, an attacker submitting 8.8.8.8; cat /etc/passwd may get both the ping and the contents of the password file. Because it yields direct execution on the server, command injection is often a straight path to full compromise — frequently used to plant a web shell for persistent access. The defense is the injection defense in general: never pass untrusted input to an interpreter; use safe APIs that don't invoke a shell; and validate input strictly.

SQL injection — the headline, deferred

The most famous member of the injection family is SQL injection (SQLi) — injecting database queries through application input, where a single injectable endpoint can lead to full database exfiltration. It sits within A05 alongside the attacks above, and it works by the same principle: untrusted input mixed into a SQL query that the database then executes as code. Because SQLi is so important, so prevalent historically, and so instructive, CEH gives it an entire dedicated module — Module 15 — so we introduce it here as part of the injection family but reserve its full treatment for next. The key point for now: SQLi is not a different kind of flaw, but the same injection root cause aimed at the database tier.

The unifying defense

Because every injection attack shares one root cause, they share one root defense: separate code from data, and never trust input. Concretely, that means using parameterized queries and prepared statements (which pass user data to the database as data, never as executable SQL), context-appropriate output encoding (which renders user data inert in HTML, JavaScript, or URLs), input validation and sanitization, and safe APIs instead of string concatenation. A Web Application Firewall adds a layer by blocking known injection patterns, and SAST/DAST tools help find these flaws, but the fundamental fix lives in the code. This single principle — code and data must stay apart — defeats the entire injection family at once, which is why it's the most valuable idea in the module.

🔓 Access & Authentication

The #1 risk, and its close relatives

If injection is the most famous web vulnerability, broken access control is the most prevalent — it has held the #1 spot in the OWASP Top 10 through 2021 and 2025. Together with its close relative, authentication failures, it represents the failure to correctly answer two fundamental questions: who are you? (authentication) and what are you allowed to do? (authorization/access control). These are distinct — a user can be perfectly authenticated yet still able to reach things they shouldn't — and both are where much of real-world web application risk actually lives. Unlike injection, these flaws are contextual: they can't be found by pattern-matching, only by understanding what the application's rules should be.

Broken access control

Access control enforces that users can only do and see what they're permitted to. It breaks in a few characteristic ways:

↔️ IDOR (horizontal access)

Insecure Direct Object Reference: the app exposes a reference like /account?id=123 and fails to check ownership, so changing it to 124 reveals another user's data. A user reaching another user's resources.

⬆️ Privilege escalation (vertical)

A normal user gains elevated permissions — reaching admin functionality by guessing a URL, tampering with a role parameter, or exploiting a missing check. A user gaining a higher role.

🔗 Forced browsing

Accessing restricted pages or functions directly by their URL, when the app only hides them from the interface rather than actually enforcing access on the server.

🌐 SSRF

Server-Side Request Forgery — tricking the server into making requests to internal systems or cloud metadata. Consolidated into broken access control in the 2025 Top 10, as it's fundamentally an access failure.

What unites these is a server that trusts the client to stay within bounds instead of enforcing the bounds itself — the "never trust the client" principle, violated. The defense is to enforce authorization on the server for every request, deny by default, and verify ownership and role on every sensitive action.

Authentication and session failures

Authentication failures (A07) break the "who are you?" question. They include weak password policies, vulnerability to credential stuffing (replaying credentials leaked from other breaches) and brute force, flawed or missing MFA, and — critically — poor session management. Session handling connects directly to Module 11: predictable session tokens, tokens not regenerated after login (session fixation), missing cookie flags, and sessions that never expire are all authentication-layer failures that enable session hijacking. The defenses echo that module: strong password handling, MFA, and robust session management with proper token generation, regeneration, expiry, and the Secure/HttpOnly/SameSite flags. Authentication and access control together form the identity backbone of a web application, and weaknesses in either undermine everything else the app tries to protect.

File upload and API weaknesses

Two more high-impact vectors round out the picture. Unrestricted file upload lets an attacker upload a malicious file — most dangerously a web shell, a script that gives remote command execution — which, if the server stores it in a web-accessible place and executes it, hands over control of the server. Defenses: validate file type and actual content (not just the extension), rename uploaded files, store them outside the web root, and never execute them. API weaknesses have become one of the most critical modern surfaces, because applications are increasingly API-driven and API inputs are frequently under-tested. The 2025 Top 10 explicitly folds API authorization failures (BOLA — broken object-level authorization, and BFLA — broken function-level authorization) into the #1 access-control category. APIs deserve the same rigor as the web front-end: authenticate and authorize every endpoint, validate every parameter, and never assume a caller is the official client — because, per the core principle, the client can't be trusted.

Why these resist automation

A recurring theme worth drawing out: access-control and authentication flaws are the hardest for tools to catch, and therefore where skilled human testing pays off most. A scanner can flag an XSS pattern in the code, but it cannot know that a normal user shouldn't be able to view invoice #124 — only the application's intended business rules define that entitlement, and those rules live in the developers' heads, not in the syntax. This is why the OWASP data shows these categories at the top despite decades of automated tooling, and why the tester's understanding of how the application is supposed to behave is the decisive skill. With the major attack families covered, the next section turns to the tools that support this testing.

🛠️ Tools

The intercepting proxy at the center

Web application testing revolves around one category of tool above all: the intercepting proxy. Because the browser is the client and the attacker controls it, the essential capability is to sit between browser and server and see, modify, and replay every request. This is how a tester bypasses client-side controls, tampers with parameters, and probes inputs the interface never meant to expose. Two proxies dominate the field, and knowing them is the core practical skill of this module.

🧰 Burp Suite

The industry-standard web application testing platform. Its proxy intercepts and lets you modify traffic; its Repeater replays and tweaks requests; its Intruder fuzzes inputs at scale; and its Scanner automates detection of common flaws. The tool professional web testers live in.

🕷️ OWASP ZAP

The leading free, open-source alternative from OWASP itself. It offers intercepting proxy, automated scanning, and spidering, and is well suited to learning, to CI/CD integration, and to teams that need a capable no-cost option.

DAST, SAST, and SCA — the testing spectrum

Web application security tools fall into a few complementary categories, and understanding the distinction is itself exam-relevant. DAST (Dynamic Application Security Testing) tests the running application from the outside, as an attacker would — Burp and ZAP are DAST tools, good at finding injection, XSS, misconfiguration, and runtime access-control issues. SAST (Static Application Security Testing) analyzes the source code without running it (tools like Semgrep, SonarQube, Checkmarx), catching injection and crypto flaws early, before commit. SCA (Software Composition Analysis) inspects third-party dependencies for known-vulnerable components (Snyk, OWASP Dependency-Check) — directly addressing the supply-chain category new to the 2025 Top 10. A mature program uses all three: SAST and SCA in the pipeline, DAST against running builds, and manual penetration testing to validate everything in context.

Supporting tools and practice targets

📁 Discovery & scanning

Gobuster and dirb (directory brute-forcing, from Module 13), Nikto (server-level checks), and specialized scanners for APIs and specific frameworks help map the application and surface known issues before manual testing begins.

🎯 Deliberately-vulnerable apps

DVWA, OWASP Juice Shop, and WebGoat are purpose-built vulnerable applications for practicing every technique in this module legally and safely — the right place to build hands-on skill before any authorized engagement.

The AI dimension

CEH v13 emphasizes AI-assisted security testing, and web application testing is where it's landing fastest. AI now helps generate test payloads, triage scanner output, and reason about multi-step exploits that traditional scanners miss — the chained, context-dependent attacks that have always needed human insight. But there's a double edge worth noting: research shows that AI coding assistants frequently generate code containing exactly the flaws in this module — injection patterns, authentication weaknesses, cryptographic mistakes — so as AI writes more of the world's web applications, the demand for testers who can find these flaws rises rather than falls. As throughout the course, AI is a powerful accelerant on both sides, layered on top of the fundamentals; the tester who understands why a vulnerability exists remains the one who can find the ones the tools miss.

🛡️ Countermeasures

Security has to be built in, not bolted on

The defining lesson of web application defense is that, unlike a web server you can patch, an application's security lives in how it was written. You cannot buy a patch for a logic flaw or an authorization mistake in bespoke code — it has to be prevented in development or fixed in the source. This makes secure coding the foundation of everything here, with other controls as reinforcing layers. The good news is that the vast, varied attack surface of web applications is defended by a surprisingly small set of durable principles, each of which counters whole categories of the OWASP Top 10 at once.

The core secure-coding principles

🚫 Never trust input

Validate and sanitize all input on the server, treating everything from the client as potentially hostile. This is the root defense — it underlies protection against injection, XSS, and much else, and it directly enacts the "never trust the client" principle.

🔀 Separate code from data

Use parameterized queries, prepared statements, and safe APIs so untrusted data can never be executed as code, and encode output for its context so it renders inert. This single principle defeats the entire injection family.

🔒 Enforce access server-side

Check authorization on the server for every request, deny by default, and verify ownership and role on every sensitive action and API endpoint. This addresses the #1 OWASP category, which no tool can fully catch for you.

🪪 Robust auth & sessions

Strong password handling, MFA, and proper session management — unpredictable tokens, regeneration after login, expiry, and secure cookie flags — close the authentication and session-hijacking gaps.

Shift left: security across the lifecycle

Because application flaws are cheapest to fix early and most expensive to fix in production, modern practice shifts security left — earlier into the development lifecycle. This is the direct answer to the 2025 Top 10's emphasis on Insecure Design and Supply Chain: threat modeling during design catches architectural flaws before a line of code is written; SAST in the pipeline catches injection and crypto bugs at commit; SCA flags vulnerable dependencies before they ship; and DAST plus manual testing validate the running application. Security becomes a continuous property of the development process rather than a one-time test at the end. The 2025 list's message is precisely this: risk has shifted from isolated coding bugs toward the security of the whole software ecosystem and lifecycle, and defense must follow.

Reinforcing layers

On top of secure coding, several runtime controls add defense in depth. A Web Application Firewall (WAF) filters malicious requests — blocking known injection and XSS patterns and providing virtual patching while a real fix is developed — though it's a layer, never a substitute for fixing the code. Security response headers (Content-Security-Policy, HSTS, X-Content-Type-Options) harden the browser side. Comprehensive logging and alerting — the concern of OWASP A09 — ensures attacks are detected and can be acted on in time, since logs without alerting have little value. And regular penetration testing and code review — running the very techniques of this module against your own applications — find the flaws before attackers do, closing the loop between offense and defense that runs through the whole course.

The through-line

Step back and the sprawling world of web application security reduces to a few ideas: don't trust the client, keep code and data separate, enforce access on the server, handle identity and sessions properly, and build security in throughout the lifecycle rather than bolting it on at the end. Every item in the OWASP Top 10 is, at root, a violation of one of these; every countermeasure is an application of one. That is the coherence beneath the complexity, and internalizing it is what lets an ethical hacker both find the flaws in a running application and help developers build applications that don't have them. With the application layer covered, the course turns to the single most consequential application vulnerability of all, in its own dedicated module: SQL injection.
