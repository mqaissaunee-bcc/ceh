Overview — what this lab is really teaching

Cryptography is the foundation under almost every defense in this course — the password hashes of Lab 08, the TLS certificates of Lab 17, the encrypted traffic that defeats Lab 12. This lab pins down the two most important building blocks by hand: hashing (watching a hash change as you edit text) and encryption (encrypting and decrypting a message). It's Module 20: Cryptography.

The one distinction that unlocks everything: hashing is one-way (for integrity — you can't get the input back), while encryption is two-way (for confidentiality — the right key reverses it). Mixing those two up is the most common crypto mistake, and this lab is designed to make the difference stick.

The environment you're working in

You work with cryptography utilities on the pod's workstation — a hashing tool and an encrypt/decrypt tool — entering text and watching the output. Everything is local and hands-on; there's no target, just the math.

Walkthrough

Task 1 — Watch a hash change

1 The avalanche effect

Hash a string, note the output, then change a single character and hash it again. The two hashes are completely different — not "mostly the same with one change," but totally unrelated. That's the avalanche effect, and it's what makes hashes useful for integrity: any tampering, however small, is instantly visible.

# the command-line equivalent
root@kali:~# echo -n "hello" | sha256sum
root@kali:~# echo -n "hellp" | sha256sum   # one letter changed

Notice too that the hash is always the same length regardless of input size, and that you can't run it backwards — there's no "un-hash." That one-way property is the whole point.

How the lab shows it

The lab uses CrypTool on WinOS: type a line, open Indiv. Procedures → Hash → Hash Demonstration, and watch the MD5 hash and the live "difference" field change as you edit even one character. Then switch the algorithm to SHA-256 — the hash is completely different and noticeably longer.

Task 2 — Encrypt and decrypt

2 A reversible transformation

Now encrypt a message with a key, look at the unreadable ciphertext, then decrypt it with the same key to get the original back. Unlike hashing, this is reversible — which is the whole idea of confidentiality: scramble it for everyone except whoever holds the key.

# symmetric encrypt / decrypt with one shared key
root@kali:~# openssl enc -aes-256-cbc -pbkdf2 -in msg.txt -out msg.enc
root@kali:~# openssl enc -d -aes-256-cbc -pbkdf2 -in msg.enc -out msg.dec

This is symmetric encryption: one shared key both locks and unlocks. The catch it raises — how do two parties share that key safely? — is exactly what asymmetric crypto (the public/private pairs of Lab 17) was invented to solve.

Reference — beyond the lab

Hashing vs. encryption

HashingEncryption
DirectionOne-way (irreversible)Two-way (reversible with key)
PurposeIntegrity, password storageConfidentiality
Output sizeFixedVaries with input
ExamplesSHA-256, SHA-3, bcryptAES, RSA, ChaCha20

Symmetric vs. asymmetric

SymmetricAsymmetric
KeysOne shared keyPublic + private pair
SpeedFast (bulk data)Slow (small data / key exchange)
SolvesEncrypting lots of dataSharing keys, signatures, identity
ExamplesAES, ChaCha20RSA, ECC, Diffie-Hellman

In practice the two combine: asymmetric crypto securely exchanges a symmetric key, then fast symmetric crypto encrypts the actual traffic — which is exactly how TLS works. In the lab, CrypTool does this through Encrypt/Decrypt → Symmetric (modern) → AES (CBC) with a shared key (e.g. AA AA AA BB BB BB CC CC CC), and a Hybrid → RSA-AES option that demonstrates exactly that combination.

"Isn't encoding the same as encryption?"Confusing Base64 with encryptionEncoding (Base64) has no key and anyone can reverse it — it's not security.

The defender's view

Use strong, standard crypto correctly — and look ahead

The failures are almost never the math; they're bad choices and bad implementation.

  • Pick modern algorithms — AES-256 and SHA-256/3 for general use; bcrypt/scrypt/Argon2 for passwords. Retire MD5, SHA-1, DES.
  • Don't roll your own — use vetted libraries; most real breaks are implementation bugs, not broken ciphers.
  • Manage keys well — generate strong keys, store them securely, rotate them, and never hard-code them.
  • Hash passwords, encrypt data — match the tool to the job; salt password hashes (Lab 08).
  • Plan for post-quantum — adversaries harvest encrypted data now to decrypt later; begin tracking the NIST post-quantum standards.

Check yourself

1. In one line, how does hashing differ from encryption?

Hashing is one-way (irreversible) and used for integrity; encryption is two-way (reversible with a key) and used for confidentiality.

2. You change one character of the input and the hash changes completely. What's that called, and why does it matter?

The avalanche effect — it means any tampering, however small, produces an obviously different hash, which is what makes hashing useful for integrity checks.

3. Why can't you share a symmetric key over the open internet by itself, and what fixes that?

Anyone intercepting it could then decrypt everything. Asymmetric cryptography (public/private keys, key exchange) is used to share the symmetric key securely.

4. Is Base64 a form of encryption?

No — it's encoding. It has no key and anyone can reverse it, so it provides no confidentiality.

Cheat sheet

Concepts

  • Hash = one-way (integrity)
  • Encrypt = two-way (confidentiality)
  • Avalanche: tiny change → totally different hash
  • Symmetric = one key; asymmetric = key pair
  • Encoding (Base64) ≠ encryption

Commands & choices

  • echo -n "x" | sha256sum
  • openssl enc -aes-256-cbc -pbkdf2 -in f -out f.enc
  • openssl enc -d -aes-256-cbc -pbkdf2 ...
  • Use AES-256, SHA-256/3, Argon2/bcrypt
  • Retire MD5/SHA-1/DES; watch post-quantum
