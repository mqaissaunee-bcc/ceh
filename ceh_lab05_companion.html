Overview — what this lab is really teaching

Scanning and enumeration told you what's running. Vulnerability analysis asks the next question: which of those things is weak? OpenVAS automates that by firing thousands of Network Vulnerability Tests (NVTs) at a target and matching what it finds against a database of known flaws. This is Module 5: Vulnerability Analysis.

The judgment to build here is that a scanner reports potential vulnerabilities from signatures — it is not proof. Your job is to read the report, rank findings by CVSS, and separate real issues from false positives. A scanner makes you fast; it doesn't make you right.

Currency note — OpenVAS is now Greenbone

"OpenVAS" is now part of Greenbone Vulnerability Management (GVM); the web interface is the Greenbone Security Assistant (GSA) and the service is managed with gvm-start / gvm-check-setup. The lab's menu path and concepts still hold — just expect "Greenbone" branding in current builds.

The environment you're working in

OpenVAS runs on Kali and is driven through a web interface in the browser, not the terminal. Your target is the deliberately vulnerable OWASP BWA host, which will light the report up nicely. The one thing to know going in: the scanner is only as good as its feed (its NVT database), and that feed has to finish syncing before results mean anything.

Scan walkthrough

This lab is driven through the Greenbone web interface. Here's the workflow and what each choice means.

Task 1 — Initial setup

1 Start OpenVAS and sign in

From the Kali Application Launcher: 02-Vulnerability Analysis > openvas start (equivalently gvm-start). It takes a few minutes to bring all the services up. Then log into the Greenbone Security Assistant web interface with username admin and password password.

2 Explore SecInfo and the CVSS Calculator

Open SecInfo > Dashboard to see the scanner's knowledge base — the Network Vulnerability Tests (NVTs) and CVEs charted by severity and CVSS. Then open Extras > CVSS Calculator: feed it the base-metric vectors (attack vector, complexity, privileges, user interaction, and the CIA impacts) and watch it derive the 0–10 score. This is exactly how "High" and "Critical" are calculated.

Task 2 — Quick scan with the Task Wizard

3 One-click scan

Go to Scans > Tasks and click the purple Task Wizard icon (top-left). In the Quick start field, type the OWASP target 192.168.68.12 and click Start Scan. The wizard uses the Full and fast config by default. The scan takes 10–20 minutes; wait for the progress bar to reach 100% / Done.

If you hit an authentication error

The page refreshes periodically, and the small SQLite install has a known permission quirk. If an auth error appears, click "Assumed sane state" and the page reloads — it's a product bug, not your mistake.

4 Read the report

When the scan finishes, click the 1 under the Reports Total column, then the date to open the full report. Findings are grouped by severity, each tied to a CVE and a CVSS score, with a QoD (Quality of Detection) showing how confident the scanner is.

Task 3 — Customized scan

5 Inspect a config, then build a target and task by hand

Open Configuration > Scan Configs and click Full and very deep ultimate — scroll the NVT families it enables (including Nmap scripts) to see how much deeper it reaches than the quick scan. Then create the pieces manually:

  • Configuration > Targets → New Target (star icon): Name OWASP, Hosts → Manual → 192.168.68.12, Alive Test → Consider Alive (so a host ignoring pings isn't skipped) → Create.
  • Scans > Tasks → New Task (star icon): Name OWASP-Scan, Scan Targets OWASP, Scan Config Full and very deep ultimate → Create.
  • Click the OWASP-Scan task, then the green Start arrow. This runs much longer than the quick scan; use the yellow Stop square when you've seen enough.
Depth vs. time vs. safety

"Ultimate" configs include checks that can crash fragile services — on production you'd think twice, but on the practice target, go deep to see more.

The defender's view

Same tool, both chairs

Vulnerability scanning is a blue-team activity. The report an attacker uses to find a way in is the same report you use to close the door first.

  • Scan yourself, authenticated, on a schedule — find it before someone else does, with the depth that credentials unlock.
  • Prioritize with more than CVSS — combine severity with exploitability signals (EPSS, the CISA KEV catalog) so you patch what's actually being exploited first.
  • Treat the report as a backlog — track findings to remediation; re-scan to confirm the fix.
  • Remember it's noisy — scanning lights up IDS. Coordinate authorized scans so your own sensors don't chase them.

CEH v13 exam relevance

Hands-on side of Module 5: Vulnerability Analysis. High-yield facts:

  • Assessment vs. penetration test — scanning finds and ranks potential weaknesses; a pentest proves exploitability.
  • CVSS — base/temporal/environmental metric groups and the 0–10 severity bands.
  • CVE / NVD and how a scanner's NVTs map findings to known entries.
  • Authenticated vs. unauthenticated scans, and why credentials change the results.
  • False positives and false negatives, and the role of QoD/validation.
  • Scanner categories: network, host, application, and database.

Check yourself

1. A scanner reports a "Critical" finding. Is that proof the host is exploitable?

No. A scanner reports a potential vulnerability from a signature match. You validate it (check the QoD and detection method, or exploit it in a controlled test) before treating it as confirmed.

2. Why does an authenticated scan usually find far more than an unauthenticated one?

With credentials the scanner can log in and inspect installed patch levels, configuration, and local issues it can only guess at from the outside.

3. A CVSS score of 7.5 falls in which severity band?

High (7.0–8.9). Critical begins at 9.0.

4. Your scan of a known-vulnerable host comes back nearly empty. First thing to check?

Whether the NVT feed finished syncing — with no up-to-date tests, the scanner has little to check against.
