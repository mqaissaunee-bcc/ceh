Overview — what this lab is really teaching

Before you ever send a packet at a target, DNS will tell you a surprising amount about it: the addresses of its servers, who handles its mail, which name servers are authoritative, and sometimes — through a misconfiguration — its entire internal map. That's DNS footprinting, and it sits in Module 2: Footprinting & Reconnaissance.

You'll use the two tools every analyst reaches for:

  • nslookup — on every Windows and Linux box, with an interactive mode that's great for exploring record by record.
  • dig — richer, more precise, and scriptable; the tool you'll graduate to.

The headline concept to walk away with is the zone transfer (AXFR): a replication feature that, left open, hands an attacker a complete list of a domain's records in one request. Finding a server that allows it is a genuine, reportable finding.

The environment you're working in

You work from Kali. The lab runs a DNS server that is authoritative for the domain mylab.com and is listening only on 192.168.0.254. That last detail matters: unless you point your queries at that server explicitly, you'll be asking the wrong resolver and wondering why nothing comes back.

Command walkthrough

Task 1 — Footprinting with nslookup

1 Read the manual, then go interactive

root@kali:~# man nslookup
root@kali:~# nslookup

Running nslookup with no arguments drops you into interactive mode — a little prompt where you set options and fire queries one after another. This is the mode the lab uses first.

2 See and set your query server

> server
> server 192.168.0.254

server on its own shows which resolver you're currently asking. server 192.168.0.254 repoints you at the lab's authoritative DNS. Do this first — every query below depends on it.

3 Look up records by type

> mylab.com
> set type=ns
> mylab.com
> set type=mx
> mylab.com
> set type=a
> opensuse.mylab.com

set type= changes what kind of record you're asking for. Each type exposes a different slice of the target:

TypeReturnsWhy an attacker cares
AIPv4 address of a hostnameWhere to aim next
NSAuthoritative name serversThe servers that hold the zone — targets for the transfer below
MXMail exchangersMail infrastructure; phishing and spoofing surface
ANYEverything the server will giveOne query, maximum exposure (modern servers increasingly refuse it)

4 Attempt a zone transfer

> set type=axfr
> mylab.com

AXFR asks the server for a full copy of the zone — every record it holds. A properly configured server only allows this to its own secondaries and refuses you; a misconfigured one hands over the whole map.

This is the money shot of DNS recon

A successful AXFR gives you hostnames you'd never guess and the internal structure of a network in one request. That's exactly why finding an open one goes straight into the report.

📸 Screenshot for your report

Capture the result of the zone-transfer attempt (set type=axfr) — whether the server refuses it or dumps the whole zone. Either way it is a finding worth recording.

> exit

Task 2 — The same work, non-interactively, and with dig

5 One-shot nslookup with debug

root@kali:~# nslookup -type=ns -debug mylab.com 192.168.0.254

Everything you did interactively collapses into one line: record type, the -debug flag (which shows the full response including the SOA and header flags), the name, and the server to ask — all as arguments. This is the form you'd drop into a script.

6 The same query with dig

root@kali:~# dig @192.168.0.254 mylab.com ns

dig's grammar is dig @server name type. The output is more detailed and far easier to parse than nslookup's — note the clearly labelled ANSWER, AUTHORITY, and ADDITIONAL sections. For a zone transfer with dig you'd write dig @192.168.0.254 mylab.com axfr.

SymptomCauseFix
Queries return nothing / public answersStill pointed at the default resolverRun server 192.168.0.254 first (or use @192.168.0.254 with dig).
"Stuck" at the > promptYou're in nslookup interactive modeType exit to get your shell back.

The defender's view

What the blue team does about this

DNS footprinting is mostly passive, so it rarely trips an alarm — which is exactly why hardening the data itself matters.

  • Restrict zone transfers — allow-transfer limited to known secondaries; never to the world. This single control closes the AXFR finding.
  • Split-horizon DNS — serve internal names only to internal resolvers, so external queries can't map the inside.
  • Minimize exposure — don't publish records that don't need to be public; avoid descriptive hostnames that leak purpose.
  • Monitor — log and alert on AXFR attempts and high-volume querying; an IDS can flag them.

CEH v13 exam relevance

Hands-on side of Module 2: Footprinting & Reconnaissance. High-yield facts:

  • Record types and what each reveals: A, AAAA, CNAME, MX, NS, SOA, PTR, TXT, SRV.
  • SOA fields — serial, refresh, retry, expire, minimum TTL.
  • Zone transfer (AXFR) as a classic misconfiguration and finding; IXFR is the incremental version.
  • nslookup vs dig — know both; know dig's @server name type syntax.
  • Footprinting (passive, no direct contact needed) vs scanning (active) — which phase you're in.

Check yourself

1. Your lookups keep returning public internet answers, not mylab.com records. What did you skip?

Pointing at the lab's authoritative server: server 192.168.0.254 in nslookup, or @192.168.0.254 with dig.

2. What does a successful AXFR give an attacker, and why is an open one a reportable finding?

A complete copy of the zone — every hostname and record — in one request, exposing internal structure that should never be public. It should be restricted to authorized secondary servers.

3. Write the dig command to ask 192.168.0.254 for the MX records of mylab.com.

dig @192.168.0.254 mylab.com mx

4. Why might set type=any return less than you expect on a modern server?

Many resolvers now minimize or refuse ANY queries (RFC 8482) to cut abuse and amplification, so you should query specific record types.

Cheat sheet

nslookup

  • nslookup — interactive mode
  • server 192.168.0.254 — set resolver
  • set type=ns|mx|a|any|axfr
  • name.mylab.com — run the lookup
  • exit — leave interactive mode
  • nslookup -type=ns -debug name server

dig

  • dig @server name type
  • dig name +short — answer only
  • dig name +trace — from the root
  • dig @server domain axfr — zone transfer
  • dig -x IP — reverse lookup
  • whois domain — ownership data
