Overview — what this lab is really teaching

Footprinting (Lab 01) told you a target exists. Scanning tells you what is reachable and running on it. This is the second phase of the attack lifecycle, and in the CEH v13 curriculum it is Module 3: Scanning Networks.

The lab walks the same target three ways on purpose, so you can feel the trade-offs that scanning tools make:

  • Nmap — the reference tool. Deep, accurate, scriptable; slower and noisier the more you ask of it.
  • Zenmap — Nmap with a graphical front end. Same engine, friendlier output, and it shows you the command it builds — a great way to learn the flags.
  • Masscan — built for speed over the whole internet. It gives up Nmap's depth to scan enormous ranges in seconds.

The real learning objective isn't "type these commands." It's understanding that every scan is a choice between coverage, depth, speed, and stealth — and that each flag moves one of those dials at the expense of another.

Command walkthrough

Every command the lab has you type, in order, with what it does and what to watch for. Hover or tab to any command block and use Copy.

Setup

0 Disable Docker first

root@kali:~# systemctl stop docker

Docker runs its own virtual network bridges and iptables rules on Kali. Masscan uses its own TCP/IP stack and talks to the network card directly — when Docker's networking is in the way, the two collide.

This is the #1 lab-killer

Skip this step and you get a segmentation fault on the Masscan task later — with no obvious hint why. If Masscan crashes, this is almost always the reason. Run the command, then continue.

Task 1 — Reconnaissance using Nmap

1 Read the manual

root@kali:~# man nmap

Nmap has more options than any other tool in this course, plus its own scripting engine (NSE). Spacebar pages down, q quits. You won't memorize it — but knowing the man page is where the answers live is the habit that matters.

2 A default scan

root@kali:~# nmap 192.168.68.12

With no flags, Nmap scans the top 1,000 most common TCP ports (not all 65,535) and reports which are open, closed, or filtered. Because you're root, it quietly uses a SYN scan under the hood.

Read the output

"Open" = something is listening. "Filtered" = a firewall is swallowing the probe, so Nmap can't tell. That distinction is a real finding, not noise.

3 A TCP connect scan

root@kali:~# nmap -sT 192.168.68.12

-sT forces a full TCP connect scan: Nmap completes the whole three-way handshake (SYN → SYN/ACK → ACK) on every port, using the operating system's normal connect call. It needs no special privileges — but it is louder, because applications log a completed connection.

"The results look identical to the last scan"

They will here — this target only has standard, responsive TCP ports. That does not mean -sT and the default SYN scan are the same thing. They differ in mechanism (full handshake vs half-open), in privilege (connect needs none; SYN needs root), and in how loud they are. Same picture, very different footprint.

4 A fast scan

root@kali:~# nmap -F 192.168.68.12

-F ("fast") drops from the top 1,000 ports to the top 100. Quicker and quieter — but you trade away coverage.

Notice what disappears

Port 5001 is gone from this output. It's a non-standard port, so it isn't in the top-100 list. That's the whole lesson of -F in one line: speed costs you the unusual ports — which are often the interesting ones.

5 An aggressive scan

root@kali:~# nmap -A 192.168.68.12

-A is a bundle — one flag that turns on four things at once: OS detection (-O), service/version detection (-sV), default scripts (-sC), and traceroute. You get far more detail about the target.

"It froze / is taking forever"

It isn't frozen — -A is doing a lot of work and is the slowest command in this task. It's also the loudest thing you can do to a target. Give it time.

Screenshot for your report

Capture the nmap -A output showing the OS guess and the service/version detail.

6 Run the default scripts

root@kali:~# nmap -sC 192.168.68.12

-sC runs Nmap's default category of NSE scripts (equivalent to --script=default) — safe checks that pull banners, basic config, and low-risk vulnerability hints.

How does this relate to -A?

-A already includes -sC. Running -sC on its own is the "just the scripts, please" version — lighter than the full aggressive bundle.

Task 2 — Reconnaissance using Zenmap

7 Launch the GUI

root@kali:~# zenmap

Enter the target, pick a Profile (e.g. Quick scan), and — this is the part worth slowing down for — watch the Command field. Zenmap builds a real Nmap command from your choices and shows it to you. Quick scan, for instance, is just nmap -T4 -F. The GUI is a flashcard for the flags.

  • Ports / Hosts tab — the same data, organized cleanly.
  • Save Scan → scan1.xml — scans persist and can be re-loaded and combined.
  • Scan a whole network — set the target to 192.168.0.0/24 to sweep the subnet.
  • Topology tab — a network map you can export straight into an assessment report.
The /24 means

192.168.0.0/24 is CIDR for "all 256 addresses from .0 to .255." One target just became the whole LAN.

Screenshot for your report

Capture Zenmap’s Topology tab — that network map is exactly the kind of figure that belongs in an assessment report.

Currency note — Zenmap in 2026

Zenmap is still a fine learning aid, but it's no longer installed by default in current Kali, and modern workflows lean on the Nmap CLI (its XML output feeds other tools). Learn the GUI to see the flags; live on the command line.

Task 3 — Reconnaissance using Masscan

8 Manual, then nmap-style help

root@kali:~# man masscan
root@kali:~# masscan --nmap

--nmap prints the Nmap-compatible options Masscan understands — a bridge for people who already think in Nmap flags.

9 A fast SYN sweep

root@kali:~# masscan -sS 192.168.0.0/24 -p 80

This asks: across all 256 addresses on the LAN, who has port 80 open? -sS is a SYN scan (Masscan's default style), -p 80 limits it to one port. It finishes almost instantly — the pause at the end is just Masscan waiting for late replies.

Why Masscan feels dangerous

Masscan sends packets asynchronously at whatever rate you allow (--rate, default is very high). On a real network that can saturate links or trip every alarm. In the pod it's safe; in the wild, always set a sane --rate and have written authorization.

Options reference — beyond the lab

The lab uses a handful of flags. Here's the fuller toolkit, so you understand the tool and not just the keystrokes. Learn one scanner deeply and you can pick up its competitors fast.

Nmap — scan types

FlagScanRoot?Notes
-sSSYN / half-openYesNmap's default when privileged. Sends SYN, never completes the handshake. Faster, quieter.
-sTTCP connectNoFull handshake via the OS. The fallback when you aren't root; more likely to be logged.
-sUUDPYesSlow but essential — DNS, SNMP, DHCP live on UDP and a TCP scan misses them entirely.
-snPing sweepNoHost discovery only — "who's alive?" — no port scan.
-sF / -sN / -sXFIN / NULL / XmasYesStealth/evasion scans that exploit how the TCP spec handles odd flag combinations.

Nmap — scope, detection, output

FlagDoes
-p 80,443 · -p 1-1024 · -p-Choose ports: a list, a range, or -p- for all 65,535.
--top-ports NScan the N most common ports.
-PnSkip host discovery — treat the target as up. Essential when a host blocks ping.
-sV · -OService/version detection · OS detection.
-sC · --script=NAMEDefault NSE scripts · a specific script or category.
-T0 … -T5Timing: -T0 paranoid-slow (evasion), -T4 a sensible LAN default, -T5 fastest/loudest.
-oN · -oX · -oG · -oASave output: normal · XML · grepable · all three at once.
-v · -n · --openVerbose · skip DNS resolution (faster) · show only open ports.

Masscan — the ones worth knowing

FlagDoes
--rate NPackets per second. The single most important knob — low on production networks, high only when you own the wire.
-p 80,443 · -p 0-65535Ports to scan.
--bannersGrab service banners (needs Masscan's own stack, which is why Docker had to go).
--exclude · --excludefileCarve out addresses you must not touch — your safety rail on real engagements.
-oL / -oG / -oX / -oJOutput as list / grepable / XML / JSON.
--open-onlyReport only open ports.

The defender's view

Remember the Security Onion box in your pod

While you scanned, the Security Onion sensor at 192.168.0.100 was watching. Everything you just did leaves a signature — and knowing what that signature looks like is half of what employers actually hire CEH holders to do.

How your three scans look from the blue team's chair:

  • Nmap default / -sT — many connection attempts from one source across many ports in seconds. Classic port-scan pattern; IDS rules (Snort/Suricata) and the firewall's scan-detection both flag it.
  • -A — the loudest. Version probes and NSE scripts send distinctive payloads that signatures recognize instantly.
  • Masscan — a burst of SYNs to one port across a whole subnet. Volumetric and obvious unless the rate is throttled right down.

Countermeasures a defender puts in place: firewall rate-limiting and scan thresholds, dropping unsolicited SYNs, IDS/IPS signatures, closing and patching unneeded services to shrink the attack surface, and honeypots to catch and study scanners. Slowing a scan (-T0/-T1) lowers the odds of tripping a threshold — the attacker's answer to the defender's threshold, and exactly the cat-and-mouse Module 12 (Evading IDS) picks up.

CEH v13 exam relevance

This lab is the hands-on side of Module 3: Scanning Networks. High-yield facts that show up on the exam:

  • The three-way handshake (SYN → SYN/ACK → ACK) — and how each scan type uses or abuses it.
  • Scan types by flag: connect (-sT, full), SYN/stealth (-sS, half-open), plus FIN/NULL/Xmas/ACK and idle (zombie) scans.
  • Which scans need privilege (anything using raw packets) and which don't (-sT).
  • Nmap's default = top 1,000 TCP ports, SYN scan when privileged.
  • Detection flags: -sV, -O, and NSE via -sC/--script.
  • Reading a scan type from a packet capture — a common question style.

Check yourself

1. Why does -sS require root while -sT does not?

-sS crafts raw packets to send a bare SYN and read the reply directly — raw-socket access needs root. -sT just asks the operating system to make a normal connection, which any user can do.

2. You skipped a setup step and Masscan segfaults. What did you miss, and why does it matter?

systemctl stop docker. Masscan uses its own network stack and collides with Docker's bridges and iptables rules, which crashes it.

3. Your default scan and -sT scan returned identical open ports. Are the two scans equivalent?

No. They returned the same picture only because this host's open ports are standard and responsive. They differ in mechanism (half-open vs full handshake), in privilege, and in how much noise/logging they generate.

4. Which single Nmap flag is roughly equal to -O -sV -sC plus traceroute — and what's the cost?

-A (aggressive). The cost is speed and stealth: it's the slowest and loudest option in the lab.

Cheat sheet

Nmap

  • nmap HOST — default top-1000 scan
  • nmap -sS HOST — SYN / stealth (root)
  • nmap -sT HOST — full connect (no root)
  • nmap -sU HOST — UDP
  • nmap -F HOST — fast, top 100
  • nmap -p- HOST — all 65,535 ports
  • nmap -Pn HOST — skip host discovery
  • nmap -sV -O HOST — versions + OS
  • nmap -sC HOST — default scripts
  • nmap -A HOST — everything, loud
  • nmap -T4 HOST — brisk LAN timing
  • nmap -oA name HOST — save all formats

Masscan

  • masscan -p80 10.0.0.0/8 — one port, huge range
  • masscan -p0-65535 CIDR — all ports
  • masscan --rate 1000 ... — throttle speed
  • masscan --banners ... — grab banners
  • masscan --exclude IP ... — stay off a host
  • masscan -oJ out.json ... — JSON output

First, always

  • systemctl stop docker — before Masscan
  • man nmap / man masscan — the answers live here
