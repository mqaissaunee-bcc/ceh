Errata for the “Hacking Web Servers” video

The 12:37 explainer video was checked line by line against Module 13, which is the authoritative source. Where the two disagree, the module is right. This page lists 31 items: 3 errors, 12 imprecise or unsupported statements, 14 omissions and 2 slide defects.

What to know before assigning the video

The video follows the module’s structure and states its main ideas correctly: the server/application distinction, the two root causes, the four-step methodology, and patching plus hardening as the core defenses. Four things need attention.

  1. Item 17: the video invents a credential-theft story for the 2021 Apache traversal flaw and never gives its ID, CVE-2021-41773. No CVE number is spoken anywhere in the video, and the knowledge check relies on two of them.
  2. Item 14: the encoding-bypass explanation blames a WAF and the operating system. The module attributes the historical bypass to IIS’s own path validation.
  3. Item 1: the title graphic shows SQL injection, XSS and broken access control, which belong to Modules 14 and 15.
  4. Item 21: credential attacks, DoS/DDoS, website defacement and man-in-the-middle are absent. Defacement is a knowledge check question.

Section 3: Software flaws 4:17–6:20

#13 4:46 ≈ Imprecise Narration

Traversal described as the OS “executing a command”

In the video

“The underlying operating system simply executes that command, walking right up the directory tree.”

In the module

Common Attacks → Directory traversal: the server “improperly handles a path,” and the ../ sequences escape the web root.

Correction

../ is a path component that gets resolved, not a command that gets executed. The flaw is that the server builds a file path from the request without canonicalizing and validating it. The video’s wording invites confusion with command injection.

#14 5:22–5:38 ✕ Error Narration

Encoding bypass attributed to a WAF and to the operating system

In the video

With overlong UTF-8 such as %c0%af, “the web application firewall looks at the payload, sees what it thinks is totally safe text and just lets it right through,” then “the underlying operating system decodes that overlong string back into a dangerous slash.”

In the module

Encodings “slip traversal sequences past naive filters, a trick that historically defeated IIS’s path validation.” In Countermeasures the WAF is the control that blocks traversal sequences, which the video itself says at 11:29.

Correction

The web server software does the decoding, not the operating system: the server checked the path, then decoded it afterwards. Describe the filter as a naive filter or the server’s own path check, and say the overlong UTF-8 case is a historical IIS flaw. Also add %2e (an encoded dot), which the module lists beside %2f.

Beyond the module text. Which component decodes the request is general knowledge about the historical IIS bug; the module says only that the trick “defeated IIS’s path validation.”

#15 5:43 ≈ Imprecise Narration

Payoff of traversal overstated as “total host compromise”

In the video

“The ultimate prize here isn’t just taking a peek at hidden files. We’re talking about total host compromise.”

In the module

“The payoff is access to configuration files, credentials, source code, or the password file.”

Correction

Directory traversal on its own is file disclosure. Host compromise needs a further step, as in the one CVE where traversal also gave code execution (next item).

#17 6:04–6:18 ✕ Error Narration

Wrong mechanism for the 2021 Apache traversal RCE, and no CVE ID

In the video

In “the infamous 2021 Apache traversal flaw,” attackers accessed “the right configuration file” and “were able to extract credentials that led straight to achieving complete remote code execution.”

In the module

Apache CVE-2021-41773 is “a path-traversal flaw that also enabled remote code execution and was exploited within a day of disclosure.” The module does not describe credential theft.

Correction

Remove the credential story. Name the flaw as CVE-2021-41773 in Apache 2.4.49, and add that it was exploited within a day. The knowledge check cites the CVE ID in questions 4 and 7, and the video never says it.

Beyond the module text. Per the Apache advisory, code execution was possible when CGI was enabled: the traversal could reach a program such as /bin/sh and the server would run it. No credentials were involved.

#20 7:24 ∅ Omission Narration

HTTP response splitting named but never explained

In the video

Response splitting is named as one of “two big ones,” then only cache poisoning is walked through. Both sit inside the Misconfigurations section.

In the module

Protocol and caching attacks: response splitting injects header data through unvalidated input reflected into a response header, so the server splits one response into two and the attacker controls the second, to poison a cache or redirect a user. Apache’s CVE-2023-38709 is cited as a recent instance. Both attacks are defended by strict input validation and careful cache configuration.

Correction

Add a short explanation, the CVE, and the defenses. Note for students that response splitting has a software-flaw example, so it does not belong purely under misconfiguration.

#21 after 7:59 ∅ Omission Not in the video

The “Access, denial, and defacement” topic is missing

In the video

The video goes from cache poisoning straight to the toolkit. The only trace is a “DDoS” label in the title graphic.

In the module

Common Attacks → Access, denial, and defacement covers four attacks: credential attacks on SSH, FTP and admin logins; DoS/DDoS, including the HTTP/2 resource-exhaustion CVEs that hit Apache, Nginx and IIS; website defacement, the visible sign that an attacker gained write access; and man-in-the-middle interception, the reason TLS everywhere matters.

Correction

This is the largest gap. Knowledge check question 8 asks “What is website defacement?” and the video cannot answer it. Send students to this part of the module.

24-hour window generalized, with no CVE IDs

In the video

In the module

#27 10:17–10:36 ≈ Imprecise Narration

KEV presented as the only triage signal; EPSS and mitigations missing

In the video

The KEV list “is the definitive triage tool.”

In the module

Patch management: same-day, out-of-band patching is warranted for a remote-code-execution flaw, or one that is KEV-flagged, or one with a high EPSS score. Prioritize “by exploitation risk, not just CVSS score.” Where patching must wait, mitigations buy time: disable the vulnerable module, add a WAF rule, or front the server with a proxy that blocks the exploit. Track the CVEs for your specific servers and versions.

Correction

Add EPSS, the RCE criterion, and the three interim mitigations.

#28 10:46 ∅ Omission Narration and slide

Hardening checklist covers about half of the module’s list

In the video

Narrated: strip default credentials, configure generic error pages, follow the CIS Benchmarks, enforce least privilege. The slide adds “banners.”

In the module

Also in the four hardening cards: remove default certificates; delete sample applications, default content and test pages; disable unnecessary modules and services; turn off directory listing; suppress the Server banner; add security response headers (HSTS, Content-Security-Policy, X-Content-Type-Options); restrict filesystem permissions on the document root and configuration; isolate the server; and NIST SP 800-44 alongside the CIS Benchmarks.

Correction

Add the missing items. Directory listing stands out, since the video spent time on it as an attack at 6:48. NIST SP 800-44 appears in the knowledge check explanation for question 10.

#29 11:04 ≈ Imprecise Narration

A low-privilege account called a “sandbox”

In the video

Running as a restricted service account “trap[s] the attacker in a low-level sandbox.”

In the module

Least privilege: run as a low-privileged service account, “never as root beyond the initial bind.” Isolation is listed as a separate measure. The Overview notes that Apache and Nginx often start as root and then drop to a service user.

Correction

A service account limits what an attacker can touch; it is not a sandbox. Keep the two controls separate, and add the start-as-root-then-drop detail.

#30 11:29–11:50 ∅ Omission Narration

WAF and TLS described without their qualifiers

In the video

A WAF “acts as a virtual patch.” TLS is listed as “strict TLS encryption” with no reason given.

In the module

A WAF provides virtual patching “while a real fix is deployed,” and blocks known exploit patterns and injection attempts as well as traversal. TLS everywhere, “with the private keys tightly protected,” defends against interception and man-in-the-middle attacks.

Correction

Say that virtual patching is temporary, and connect TLS to the man-in-the-middle attack (which the video also omits; see the Section 4 entries).
