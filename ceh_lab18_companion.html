Overview — what this lab is really teaching

The strongest firewall in the world doesn't help if a user hands over their password. Social engineering attacks the person, not the machine, and the Social-Engineer Toolkit (SET) automates the technical half — most famously, cloning a login page to harvest credentials. This is Module 9: Social Engineering.

This companion keeps the focus where it belongs for a defender: what the attack looks like, why people fall for it, and how to stop it. The single most useful outcome is being able to recognize a harvester page and knowing which controls (awareness, MFA, verification) make a stolen password worthless.

Isolated range only

SET runs here against lab machines you control. Sending phishing or cloned-login pages to real people without authorization is illegal. The value is understanding the technique to defend against it.

The environment you're working in

You run SET on Kali and "attack" a browser on another pod machine. SET hosts the cloned page on Kali; the victim machine browses to it. Nothing leaves the lab network.

Walkthrough

Task 1 — Launch SET

1 Start the toolkit and walk the menus

root@kali:~# setoolkit

SET is entirely menu-driven — accept the Terms of Service (Y), then make numbered choices. The lab's exact path to a credential harvester is:

# menu selections, in order
1   # Social-Engineering Attacks
2   # Website Attack Vectors
3   # Credential Harvester Attack Method
1   # Web Templates
192.168.9.2   # IP for the POST back (your Kali box)
2   # Google template

Rather than cloning an arbitrary site, the lab uses a built-in Web Template (Google). SET hosts that fake login on Kali and will send any submitted credentials back to the POST-back IP you gave it.

Task 2 — Modify the SET parameters

2 Set where the victim is redirected

root@kali:~# nano /etc/setoolkit/set.config

In a second terminal, edit SET's config file and set HARVESTER_REDIRECT and HARVESTER_URL — these control where the victim's browser is sent after they submit, so the fake page hands off to the real site and the victim notices nothing. Save (Ctrl+X → Y → Enter) and leave the SET terminal running.

Why the clone is convincing

It's a pixel copy of the genuine page, and the redirect makes the login "just work." The only tells are the URL and the missing valid certificate — exactly what you train users to check, and why the SSL work in Lab 17 matters.

Task 3 — Test it and read the report

3 See the credentials arrive, then open the report

From the victim machine, browse to Kali's cloned page and submit test credentials, then click Sign in. Back in the SET terminal the captured Email and Password appear in red. Press Ctrl+C to stop the harvester and generate a report.

root@kali:~# cd /root/.set/reports
root@kali:~# ls
root@kali:~# cat <report-name>.xml

SET saves a dated report under /root/.set/reports/ (type 99 a few times to back out of the menus first). The whole lesson: a password typed into the wrong page is simply gone.

The defender's view

You can't patch people — you prepare them and add backstops

Social engineering never fully goes away, so defense is layered: fewer lures reach users, trained users resist, and MFA makes a stolen password insufficient.

  • Security awareness training — teach users to check the URL and certificate, distrust unexpected login prompts, and report suspicious messages. Simulated phishing measures progress.
  • MFA everywhere — a harvested password alone can't log in. Phishing-resistant MFA (FIDO2/passkeys) also defeats real-time relay.
  • Email & web filtering — block malicious senders, links, and known harvester domains before they reach the inbox or browser.
  • Technical anti-spoofing — SPF, DKIM, and DMARC make lookalike senders harder.
  • Easy reporting + fast response — a one-click "report phish" button and a team that acts on it shrink the window of damage.

Check yourself

1. What does SET's credential harvester actually do?

It serves a cloned copy of a real login page and records any username/password typed into it, usually redirecting to the genuine site afterward so the victim doesn't notice.

2. The clone is a perfect visual copy. What two things still give it away?

The URL (it's the attacker's address) and the lack of a valid certificate for the real domain.

3. Why does MFA blunt a successful credential harvest?

The stolen password alone isn't enough to log in; the attacker also needs the second factor. Phishing-resistant MFA (passkeys/FIDO2) further defeats real-time relay.

4. Which email controls make lookalike/spoofed senders harder?

SPF, DKIM, and DMARC.
