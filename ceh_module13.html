CEH v13 Module 13: Hacking Web Servers

Hacking Web Servers

Attacking the server layer beneath the application: web server architecture, fingerprinting, directory traversal, misconfiguration, the fast-moving CVE landscape across Apache, Nginx, and IIS, and the patching and hardening that defend them.

🌐 Overview

Attacking the platform, not the app

This module begins a cluster of three on web attacks, and it targets the foundation the others build on: the web server itself. A web server is the software that hosts websites — accepting HTTP requests and returning pages, files, and data. The critical distinction to hold from the outset is between the server and the application: web server hacking targets the server software (Apache, Nginx, IIS), its configuration, and its underlying infrastructure, while web application hacking — the next module — targets the custom application logic running on top of it. A single site can be attacked at either layer, but they are distinct attack surfaces with distinct techniques. This module stays deliberately at the server layer.

Why devote a whole module to the server beneath the app? Because as network- and OS-level defenses have matured — firewalls, IDS, hardened operating systems — the web server has become one of the most exposed and most attacked components an organization runs. It has to be reachable from the internet to do its job, which means it is permanently exposed to everyone, everywhere. That exposure, combined with the server's privileged position, makes it a prime target.

Why the web server is a dangerous place to have a bug

A vulnerability in the web server itself is more dangerous than the same class of bug almost anywhere else, and understanding why frames the entire module. The web server sits at the front door and sees every single request — every header, cookie, and form submission is attacker-controllable input that the server must parse, so the attack surface is enormous and constant. It typically runs with significant privileges (Apache and Nginx often start as root before dropping to a service user; IIS runs in a broadly-privileged service account), so remote code execution in the server is a short step from total host compromise. And it has direct access to the TLS private keys that prove your HTTPS certificates are genuinely yours. Compromise the web server and you may own the whole host and its cryptographic identity — which is why these attacks matter so much.

The two root causes of web server compromise

Nearly every web server attack traces back to one of two root causes, a framing worth carrying through the whole module:

🐞 Software vulnerabilities

Flaws in the web server software itself — buffer overflows, path-traversal bugs, parsing errors — that attackers exploit, often for remote code execution. These are fixed by patching, and the web server CVE landscape moves fast: internet-exposed servers are attacked within hours of a flaw becoming public.

⚙️ Misconfiguration

Insecure settings the operator left in place — default credentials, directory listing enabled, unnecessary services, verbose errors, default certificates. These require no software flaw at all; the server does exactly what it was (mis)told to do. Fixed by hardening, not patching.

Keeping this pair in mind organizes everything else: the attacks in this module exploit one or the other, and the countermeasures are, correspondingly, disciplined patching and secure hardening.

What this module covers

We begin with architecture — how web servers are built and what the major products (Apache, Nginx, IIS) look like, since you can't attack or defend what you don't understand. Then the attack methodology — the systematic process from fingerprinting to exploitation — followed by the common attacks that target the server layer: directory traversal, misconfiguration exploitation, HTTP response splitting, cache poisoning, defacement, and more. We survey the tools of web server assessment and close with countermeasures, centered on patch management and hardening. Throughout, this module builds on the reconnaissance and scanning of Modules 2–3 (which fingerprint the server) and sets up the web-application attacks of Module 14.

Test only what you're authorized to test. Web servers are internet-facing, which makes it tempting to probe any site you can reach — but doing so without permission is illegal, exactly as with any other target. The techniques here are for authorized assessments and lab environments. Legal practice grounds like TryHackMe, Hack The Box, and deliberately-vulnerable servers you host yourself are the right places to build these skills.

🏗️ Web Server Architecture

What a web server actually does

At its core, a web server is a program that listens for HTTP(S) requests and returns responses — serving static files, or passing dynamic requests to an application and returning what it produces. But a modern web server is more than a single program; it is a stack of components, and each is a potential point of failure an attacker can target. Understanding this anatomy is what lets you reason about where a server can be attacked, rather than treating it as an opaque box.

A typical web server deployment includes the core server software (the HTTP engine itself), modules and extensions (add-ons for features like URL rewriting, authentication, or scripting language support), the configuration (the rules governing what the server does and exposes), the document root (the directory tree of files it serves), TLS/SSL components (certificates and private keys for HTTPS), and often a connection to backend application and database servers. Every one of these is part of the attack surface: a flaw in a rarely-used module, a mistake in the configuration, or an exposed file in the document root can each become the way in.

The major web servers

Three products dominate, and because each has its own architecture, configuration model, and characteristic vulnerabilities, identifying which one a target runs is a critical early step.

🪶 Apache HTTP Server

The long-dominant open-source server, predominantly on Linux/Unix. Modular and highly configurable via httpd.conf and .htaccess files. Its flexibility is a double-edged sword: enabled-but-unneeded modules and misconfigured .htaccess rules are common weaknesses. Notable CVEs include the 2021 path-traversal RCE (CVE-2021-41773).

⚡ Nginx

A high-performance server and reverse proxy with a smaller core and fewer CVEs — but the ones that land are often impactful (resolver overflows, HTTP/3 parsing bugs, mp4-module overflows). Frequently used as a load balancer and TLS terminator in front of other servers. Avoid its experimental modules in production.

🪟 Microsoft IIS

Microsoft's web server, built into Windows Server. Its historical surface includes ASP.NET authentication bypasses and HTTP.sys remote crashes. Modern Windows pushes fixes via Patch Tuesday, so keeping OS auto-updates on is essential. Tightly integrated with the Windows ecosystem and Active Directory.

Others appear regularly too: Apache Tomcat (a Java application server, target of the Log4Shell exploitation you'll see referenced), Caddy (a modern Go server with a small attack surface), and cloud/edge servers. The point is not to memorize every product but to recognize that fingerprinting the exact server and version is what unlocks the relevant vulnerabilities.

Where the server meets the application

A crucial architectural nuance for keeping this module distinct from the next: the web server rarely acts alone. For dynamic sites, it hands requests to an application layer (PHP, Java, .NET, Node.js) which may in turn query a database. The web server, the application, and the database are three distinct tiers, and each can be attacked separately. This module concerns the server tier — the HTTP engine and its configuration. The application tier (its code, input handling, and logic) is Module 14, and database attacks via the application are Module 15 (SQL Injection). Recognizing which tier a given weakness lives in is exactly what tells you which techniques apply. A directory-traversal flaw in the server is a Module 13 problem; an XSS flaw in the app's output is a Module 14 problem, even though both arrive over the same HTTP connection.

The privileged, exposed position — revisited

Architecture explains why the web server is such a high-value target, reinforcing the overview. It is the one component deliberately exposed to the entire internet, so it cannot hide behind a firewall the way internal systems can. It parses untrusted input on every request, giving attackers constant opportunities to trigger parsing flaws. It bridges the outside world and the internal application and database tiers, so compromising it can open a path deeper into the network. And it holds the TLS keys. Every architectural feature that makes a web server useful — its exposure, its input handling, its privileges, its bridging role — is also what makes it dangerous when compromised. With this anatomy in mind, the attack methodology becomes a systematic tour of these weak points.

🧭 Attack Methodology

A systematic progression

Attacking a web server follows a logical methodology that mirrors the overall hacking process, narrowed to this target. It moves from learning about the server, to finding its weaknesses, to exploiting them. Following the sequence matters: each step depends on what the previous one revealed, and skipping ahead — trying exploits before you know what you're facing — wastes effort and raises noise. The same discipline that governs a full engagement governs a web server assessment.

Step 1: Fingerprinting the server

Everything starts with identifying exactly what the target runs, because the specific server and version determine which vulnerabilities apply. Web server fingerprinting (or banner grabbing) extracts this identity from the server's own responses. The HTTP Server response header often names the software and version outright, and error pages, response quirks, and header ordering provide further tells even when the banner is suppressed.

# Grab the Server header with curl curl -I https://target.example.com # Nmap service/version detection and HTTP header script nmap -sV -p 80,443 target.example.com nmap --script http-server-header,http-headers target.example.com

The goal is to move from "there's a web server here" to "this is Apache 2.4.49 on Linux" — a precise identity that turns a vague target into a specific one with a known set of applicable exploits. Recall that the reconnaissance and scanning modules (2–3) already established these fingerprinting techniques; here they are applied specifically to the web server.

Steps 2–3: Mapping and vulnerability discovery

With the server identified, the attacker maps its structure and hunts for weaknesses. Mirroring or crawling the site reveals its directory structure, linked resources, and technologies, while directory and file brute-forcing (with tools like Gobuster) discovers resources that aren't linked anywhere — hidden admin panels, forgotten backup files, exposed configuration, and leftover test pages. These unlinked resources are often the softest targets precisely because no one remembers they're there.

Vulnerability scanning then checks the identified server against known weaknesses. A specialized web-server scanner like Nikto tests for thousands of known issues — dangerous files, outdated versions, misconfigurations, default content — while general scanners (Nessus, OpenVAS from Module 5) and Nmap's vuln scripts add coverage. The output is a prioritized list of candidate weaknesses: an outdated version with a known RCE, a misconfiguration exposing sensitive files, a directory that permits listing. This is where the two root causes from the overview become concrete findings.

Step 4: Exploitation

Finally, the attacker exploits a discovered weakness to gain access or achieve their objective. What this looks like depends entirely on the finding. An unpatched RCE vulnerability might be exploited with a ready-made module from a framework like Metasploit — the canonical modern example being Log4Shell (CVE-2021-44228) against a vulnerable Apache Tomcat, or the Apache path-traversal RCE (CVE-2021-41773). A misconfiguration might be exploited simply by requesting an exposed file or navigating a listable directory. Weak credentials on a management interface, SSH, or FTP might fall to a brute-force attack with a tool like Hydra. The specific attacks that exploitation employs — directory traversal, misconfiguration abuse, and the rest — are the subject of the next section.

Worth noting for currency: CEH v13 incorporates AI-assisted tooling into this methodology. Labs demonstrate using an AI assistant (ShellGPT) to generate and run attack commands — for instance, crafting a directory-traversal attack with Gobuster from a natural-language prompt — reflecting how AI now accelerates each step of the process, for attacker and defender alike.

💥 Common Attacks

The server-layer attack catalog

These are the attacks that target the web server itself — its software and configuration — as opposed to the application running on it. They divide naturally along the two root causes from the overview: some exploit misconfiguration (the server doing what it was wrongly told to do), and some exploit software vulnerabilities (flaws in the server code). Understanding each as an instance of one root cause or the other keeps the catalog coherent rather than a list to memorize.

Directory traversal

One of the most classic and instructive web server attacks, directory traversal (path traversal) uses ../ ("dot-dot-slash") sequences to escape the intended web root and reach files elsewhere on the filesystem. If a server improperly handles a path, an attacker can walk up the directory tree to sensitive files:

GET /../../../../etc/passwd # attempt to read the Linux password file GET /..%2f..%2f..%2fboot.ini # URL-encoded traversal (%2f = /) GET /..%c0%af..%c0%afwindows/ # overlong UTF-8 encoding (historically bypassed IIS)

Attackers use encoding — %2e for a dot, %2f for a slash, or overlong UTF-8 like %c0%ae — to slip traversal sequences past naive filters, a trick that historically defeated IIS's path validation. The payoff is access to configuration files, credentials, source code, or the password file. The canonical modern example is Apache CVE-2021-41773, a path-traversal flaw that also enabled remote code execution and was exploited within a day of disclosure. The defense is rigorous input validation that rejects traversal sequences and canonicalizes paths before use.

Misconfiguration exploitation

The most common web server weakness isn't a software bug at all — it's misconfiguration, where the server is running exactly as configured, but configured insecurely. These require no exploit code; the attacker simply takes advantage of settings the operator should have changed:

🔑 Default credentials & certificates

Management interfaces, admin panels, or bundled applications left with vendor-default usernames, passwords, or certificates — trivially guessed and widely documented.

📂 Directory listing enabled

When a directory has no index page and listing is enabled, the server displays its full contents, exposing files never meant to be browsed — backups, configs, source.

🧩 Unnecessary services & modules

Enabled-but-unused modules, sample applications, debugging features, and extra services each add attack surface for no benefit. Every active component is something to attack.

💬 Verbose error messages

Detailed errors that leak internal paths, software versions, stack traces, or database details — handing the attacker reconnaissance the server should never reveal.

Misconfiguration is pervasive because secure configuration takes deliberate effort and servers often ship insecure-by-default. This is exactly the gap that hardening standards like the CIS Benchmarks exist to close.

Protocol and caching attacks

Several attacks abuse the mechanics of HTTP and the caching layers around a web server. HTTP response splitting injects header data (via unvalidated input reflected into a response header) so the server splits one response into two — letting the attacker control the second response to poison a cache or redirect a user to a malicious site (Apache's CVE-2023-38709 is a recent instance). Web cache poisoning tricks the server or an intermediate cache into storing a malicious response, which is then served to other users — turning one crafted request into an attack against everyone who hits the cache. Both exploit the gap between how the server and its caches interpret a crafted request, and both are defended by strict input validation and careful cache configuration.

Access, denial, and defacement

Rounding out the catalog are attacks on access and availability. Credential attacks brute-force the server's management surfaces — SSH, FTP, or admin logins — with tools like Hydra, exploiting weak passwords to gain a foothold (the CEH labs practice exactly this against FTP). DoS/DDoS attacks flood the server to crash it or make it unavailable — and web servers have their own protocol-specific DoS flaws, like the HTTP/2-based resource-exhaustion CVEs that have hit Apache, Nginx, and IIS. Website defacement is the visible aftermath of a successful intrusion: altering the site's content or appearance, often to make a statement or prove the compromise — and a clear signal that the attacker gained write access. Finally, man-in-the-middle attacks intercept traffic to or from the server, which is why TLS everywhere matters as much here as it did in the session-hijacking module. Each of these, once again, traces back to either an unpatched flaw or an insecure configuration — the two threads that run through the whole module.

🛠️ Tools

The web server assessment toolkit

Web server assessment reuses much of the general toolkit from earlier modules and adds a few web-specific tools. They map naturally onto the methodology: fingerprinting tools identify the server, discovery tools map it, scanners find weaknesses, and exploitation frameworks deliver the attack. Knowing which tool serves which step — and which fits the situation — is the practical skill.

Fingerprinting and discovery

🔍 Nmap

The scanner from Module 3, applied to web servers: -sV identifies the server software and version, and HTTP-focused NSE scripts (http-server-header, http-enum, http-methods) extract headers, enumerate paths, and check configuration. The starting point for fingerprinting.

🌐 curl & browser dev tools

Simple but essential: curl -I grabs response headers to read the Server banner and security headers, and browser developer tools reveal the same plus cookies and technologies. Often the fastest first look at what a server reveals about itself.

📁 Gobuster / dirb / dirbuster

Directory and file brute-forcers that use wordlists to discover unlinked resources — admin panels, backups, config files, test pages. Gobuster is the fast modern choice; these find the hidden content that mirroring alone misses.

🧭 Netcraft & Wappalyzer

Passive fingerprinting services and extensions that identify the server, technologies, and hosting from the outside — useful reconnaissance before ever sending a probe of your own.

Vulnerability scanning and exploitation

🐞 Nikto

The classic dedicated web-server scanner. It tests for thousands of known issues — dangerous files, outdated server versions, default content, and misconfigurations — in a single run. A fast way to surface the low-hanging fruit on a web server.

🛡️ Nessus / OpenVAS

The general vulnerability scanners from Module 5, which include extensive web-server checks and map findings to known CVEs. Good for confirming version-based vulnerabilities and integrating web-server findings into a broader assessment.

💣 Metasploit

The exploitation framework: once a vulnerable server and version are identified, Metasploit often has a ready module to exploit it (e.g. Log4Shell against a vulnerable Tomcat). It turns a known CVE into working access.

🔨 Hydra

The online password-cracker from Module 6, used here against a web server's management surfaces — SSH, FTP, and login forms — to exploit weak credentials. The tool behind the credential attacks in the previous section.

Choosing tools — and the AI shift

The selection logic follows the methodology: Nmap and curl to fingerprint, Gobuster to discover hidden paths, Nikto (and Nessus/OpenVAS) to scan for known weaknesses, and Metasploit or Hydra to exploit what you find. A real assessment chains them — fingerprint with Nmap, brute-force directories with Gobuster, scan with Nikto, then exploit the best finding. And reflecting CEH v13's modernization, AI assistants now sit alongside this toolkit: the labs demonstrate using ShellGPT to generate and run these commands from natural-language prompts, accelerating the workflow. As throughout the course, AI is an accelerant on top of the fundamentals — it helps you drive the tools faster, but understanding what each tool does and why remains the core skill.

Practice legally. These tools should be pointed only at servers you own or are explicitly authorized to test. Deliberately vulnerable targets — DVWA, OWASP-provided VMs, and the web-server labs on TryHackMe and Hack The Box — exist so you can practice the full toolkit safely.

🛡️ Countermeasures

Two root causes, two core defenses

Because virtually every web server attack exploits either a software vulnerability or a misconfiguration, the defense follows directly: patch management addresses the first, and secure hardening addresses the second. Get these two right and you close the great majority of the attack surface; the remaining controls are reinforcing layers. This clean mapping — root causes to countermeasures — is the organizing idea of web server defense.

Patch management: speed is the whole game

For web servers, patching is uniquely urgent, because the server sits at the front door where every internet-exposed instance running a vulnerable version is an immediate target. The historical record is stark: headline web-server RCEs like Apache Path Traversal (CVE-2021-41773) and Log4Shell (CVE-2021-44228) crossed from public disclosure to active mass-exploitation within about 24 hours. There is no "patch when convenient" for an internet-facing web server.

Effective patch management means tracking the CVEs affecting your specific servers and versions, and prioritizing by real-world risk: a remote-code-execution flaw, or one that is KEV-flagged (on CISA's Known Exploited Vulnerabilities list) or carries a high EPSS score (from Module 5's prioritization concepts), warrants same-day, out-of-band patching. Where an immediate update isn't possible, mitigations buy time — disabling a vulnerable module, adding a WAF rule, or fronting the server with a proxy that blocks the exploit. The principle: for the front-door server, patch fast and prioritize by exploitation risk, not just CVSS score.

Hardening: remove everything you don't need

Hardening counters the misconfiguration root cause by making the server's configuration secure-by-intent rather than insecure-by-default. The unifying principle is minimize the attack surface — every feature, module, service, and file that isn't needed is removed, because it can't be attacked if it isn't there.

🧹 Strip the defaults

Change or remove all default credentials and certificates. Delete sample applications, default content, and test pages. Disable unnecessary modules and services. Turn off directory listing everywhere it isn't explicitly needed.

🤐 Suppress information leaks

Configure generic error pages that don't leak paths, versions, or stack traces. Suppress or minimize the Server banner. Add security response headers (HSTS, Content-Security-Policy, X-Content-Type-Options).

🔒 Least privilege

Run the server as a low-privileged service account, never as root beyond the initial bind. Restrict filesystem permissions on the document root and configuration. Isolate the server so a compromise doesn't reach the whole host.

📋 Follow a standard

Don't harden from memory — follow an established baseline. The CIS Benchmarks provide vetted, step-by-step secure configurations for Apache, Nginx, and IIS, and NIST SP 800-44 gives web-server security guidance. These encode hard-won best practice.

Reinforcing layers

Patching and hardening are the foundation; several layers reinforce them. A Web Application Firewall (WAF) sits in front of the server and filters malicious requests — blocking traversal sequences, known exploit patterns, and injection attempts — providing virtual patching while a real fix is deployed. TLS everywhere (with the private keys tightly protected) defends against the interception and man-in-the-middle attacks. Continuous monitoring and logging — feeding a SIEM — catches the reconnaissance and exploitation attempts that precede a breach, turning the web server's abundant logs into early warning. And regular security assessment — running the very tools from the previous section against your own servers — finds the exposures and misconfigurations before an attacker does, closing the loop between offense and defense.

The defender's mindset

The web server's defining trait — permanent, privileged exposure to the entire internet — is exactly what makes disciplined defense non-negotiable. There is no obscurity to hide behind and no firewall that can fully shield a component that must answer every request. So the defender patches fast, hardens thoroughly, strips away everything unneeded, watches the logs, and tests continuously. Do that, and the two root causes of compromise — vulnerable software and insecure configuration — are systematically addressed. With the server layer secured, attention turns to what runs on top of it: the web application itself, and its far larger and more varied attack surface, which is the subject of Module 14.
