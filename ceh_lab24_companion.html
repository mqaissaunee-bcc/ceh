Overview — what this lab is really teaching

Two web attacks in one lab: first an automated vulnerability sweep with Vega, then the sharper lesson — spoofing an authentication cookie to become another user without ever knowing their password. That second part is session hijacking (Module 11), applied to a web app (Module 14).

The core idea: after you log in, the server trusts a token in a cookie to remember who you are. If that token is predictable or stealable, an attacker can simply present someone else's — and the server, trusting the cookie, hands over their account.

The environment you're working in

You work in a browser against the pod's vulnerable web application, with Vega (the Subgraph scanner) on the Windows VM for the scanning half. For the cookie work you'll log in with the app's own accounts and inspect cookies through the browser's developer tools.

Walkthrough

Task 1 — Scan with Vega

1 Run an automated web scan

Open Vega, point a scan at the target URL, and let it crawl and test. Like Nikto or ZAP, it reports likely issues — cross-site scripting, injection, insecure cookies — each with a severity and the request that triggered it. Expand a finding to read the detail.

Task 2 — Spoof an authentication cookie

2 Log in and read your cookie

Log into the app (the lab uses an Administrator account — substitute the password from your lab sheet), then open the browser's developer tools and find the AuthCookie among the site's cookies. Note its value.

3 Compare two users' cookies

Capture the AuthCookie for a second account (the lab uses alice) and line the two values up. The giveaway: the first several characters are identical. That shared, predictable structure means the token isn't random — it's guessable, and therefore forgeable.

📸 Screenshot for your report

Capture the two AuthCookie values side by side, showing the matching leading characters that reveal the weak pattern.

Why "they share a prefix" is the whole finding

A secure session token is long and random, so two users' tokens should look nothing alike. Shared structure means the server is deriving the token from something predictable — exactly what lets an attacker craft a valid one.

4 Become the other user

Replace the value of your AuthCookie with alice's value (editing the cookie in dev tools) and reload. The server reads the cookie, believes you're alice, and logs you into her account — no password required. That's session hijacking by cookie substitution.

Reference — beyond the lab

How sessions get hijacked

TechniqueHow the token is obtained
Prediction / forgeryToken is guessable (this lab) — craft a valid one
Sniffing / session sidejackingCapture it off an unencrypted connection (Lab 06)
XSS theftScript reads a non-HttpOnly cookie and exfiltrates it
Session fixationForce a victim to use a token the attacker already knows

The defender's view

A session token is a password — treat it like one

Everything here fails if the token is random, protected in transit, and validated server-side.

  • Unpredictable tokens — long, cryptographically random session IDs with no derivable structure. This alone defeats the lab's attack.
  • Set the cookie flags — HttpOnly (blocks XSS theft), Secure (blocks sniffing), SameSite (blocks CSRF).
  • TLS everywhere — so a token can't be captured in transit.
  • Server-side session validation — bind the session to context and re-check it; don't trust the cookie's claims blindly.
  • Rotate and expire — issue a new token at login and privilege change; expire idle sessions and offer real logout.

CEH v13 exam relevance

Spans Module 11: Session Hijacking and Module 14: Hacking Web Applications. High-yield facts:

  • Session hijacking at the application level — stealing or forging the session token rather than the password.
  • Ways to obtain a token: prediction, sniffing, XSS, session fixation.
  • Cookie flags: HttpOnly, Secure, SameSite — and what each stops.
  • Why random, server-validated session IDs are the defense.

Check yourself

1. How can an attacker take over an account without knowing the password here?

By presenting a valid session token (cookie) for that account. The server trusts the cookie to identify the user, so a stolen or forged token is enough.

2. Two users' auth cookies share their first several characters. Why is that a vulnerability?

It shows the token isn't random — it has predictable structure — so an attacker can guess or forge a valid token for another user.

3. Which cookie flag stops a cross-site scripting payload from stealing the session cookie?

HttpOnly — it prevents JavaScript from reading the cookie.

4. What single property of a session token would have defeated this entire attack?

Being long and cryptographically random (no predictable structure), so one user's token tells you nothing about another's.

Cheat sheet

The attack

  • Vega / ZAP / Burp — automated web scan
  • Log in → dev tools → find AuthCookie
  • Compare two users' tokens → spot the pattern
  • Replace your cookie with the victim's → reload
  • = session hijacking by cookie substitution

The defense

  • Random, long session tokens
  • HttpOnly · Secure · SameSite
  • TLS everywhere
  • Server-side validation; rotate on login
  • Idle timeout + real logout
