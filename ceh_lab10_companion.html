Overview — what this lab is really teaching

Web applications are the biggest attack surface most organizations have. This lab is your first pass over one: scan it with Nikto, then put Burp Suite — the intercepting proxy every web tester lives in — between your browser and the app so you can see and manipulate every request. It's Module 14: Hacking Web Applications.

The idea to internalize is that the browser is a suggestion, not a boundary. Once Burp sits in the middle, every hidden field, cookie, and parameter the server trusts is yours to read and change. Web security is about what the server does when the client misbehaves.

The environment you're working in

You work from Kali against the OWASP BWA web app at 192.168.68.12 — a server built to be full of holes. Nikto runs from the terminal; Burp runs as a GUI with your browser pointed through it as a proxy.

Command walkthrough

Task 1 — Scan with Nikto

1 A baseline web-server scan

root@kali:~# nikto -help
root@kali:~# nikto -host 192.168.68.12
root@kali:~# nikto -host 192.168.68.12 -output report.html

Nikto checks a web server for outdated software, dangerous files, and misconfigurations, then (with -output) saves a shareable report. After the broad scan, the lab narrows in with specific plugin categories (-list-plugins shows them all):

root@kali:~# nikto -Plugins outdated -host 192.168.68.12
root@kali:~# nikto -Plugins httpoptions -host 192.168.68.12
root@kali:~# nikto -Plugins msgs -host 192.168.68.12
root@kali:~# nikto -Plugins tests -host 192.168.68.12

Each targets one thing: outdated flags stale software, httpoptions reveals the server accepts all HTTP methods (susceptible to cross-site tracing), msgs checks server messages, and tests runs standard checks (here flagging a buffer-overflow exposure). (See Lab 19 for Nikto in the scanning methodology.)

Task 2 — Put Burp in the middle

2 Launch Burp and proxy the browser

root@kali:~# burpsuite

Burp's Proxy listens on 127.0.0.1:8080. Point the browser's proxy settings at it, and now every request the browser makes passes through Burp first. With Intercept on, Burp pauses each request so you can read or edit it before it reaches the server; the lab turns Intercept off so traffic just flows and is logged. Point Firefox's proxy at 127.0.0.1:8080 (Preferences → Network Settings → Manual proxy, "Use this proxy for all protocols"), browse to 192.168.68.12, then on the Target tab right-click the host and Add to scope so the site map and intercept focus on it. The lab then opens Damn Vulnerable Web Application and logs in with admin / admin to map it further.

The one setup gotcha

To intercept HTTPS without certificate errors, install Burp's CA certificate in the browser. Without it, TLS sites throw warnings and won't load cleanly.

3 Build a site map

Just browse the application normally. Burp passively records every page, parameter, and endpoint into the Target > Site map — a complete inventory of the app's attack surface, including links you'd never have clicked. This is reconnaissance without a single extra request.

Task 3 — Brute force a login

4 Automate guesses with Intruder

Send a login request to Intruder, mark the username/password fields as payload positions, load a wordlist, and run the attack. Burp replays the request hundreds of times, swapping in each guess, and you sort the results by response length or status to spot the one that worked.

Screenshot for your report

Capture the Intruder results table with the successful attempt standing out (different length or status code).

Why the "odd one out" works

A failed login and a successful one almost always return different-sized responses. Sorting by length surfaces the hit without reading every row.

The defender's view

Never trust the client

Every technique here works because the client can lie. The defense is to validate and enforce everything on the server, where the attacker can't reach.

  • Stop brute force — account lockout or progressive delays, rate limiting, CAPTCHA on repeated failures, and MFA so a guessed password isn't enough.
  • Server-side validation — never trust hidden fields, prices, or roles sent by the browser; re-check them on the server.
  • Patch and harden the server — the outdated-software and dangerous-file findings Nikto reports are a direct fix list.
  • Don't leak — generic login errors (not "user not found" vs "wrong password"), suppressed version banners, and no directory listing.
  • Put a WAF in front — a layer that catches common automated attacks, logging them for your sensors.

Check yourself

1. What does putting Burp between your browser and the app let you do that the browser alone won't?

See and edit every request — including hidden fields, cookies, and parameters — before it reaches the server, so you can test what the server does when the client misbehaves.

2. HTTPS sites won't load through Burp. What's the usual fix?

Install Burp's CA certificate in the browser so it trusts Burp's interception.

3. In an Intruder brute force, how do you spot the successful login quickly?

Sort results by response length or status code — the successful attempt usually differs from all the failures.

4. Name two controls that defeat automated login brute forcing.

Any two: account lockout / progressive delays, rate limiting, CAPTCHA, and MFA.

Cheat sheet

Nikto

  • nikto -host IP -output report.html
  • nikto -list-plugins

Burp workflow

  • burpsuite · proxy 127.0.0.1:8080
  • Install Burp CA for HTTPS
  • Browse → Target → Site map
  • Repeater — resend/edit one request
  • Intruder — positions + wordlist → sort by length
