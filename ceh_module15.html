SQL Injection

🗄️ Overview

The vulnerability that refuses to die

Modules 13 and 14 both pointed here, and this module makes good on the promise: a dedicated, in-depth treatment of SQL injection, the most consequential single application vulnerability in the history of the web. SQLi was introduced in the previous module as one member of the injection family (OWASP A05); here we take it apart completely. It earns a whole module for three reasons that are worth stating plainly at the outset. It is still everywhere — despite being understood for more than two decades, it remains one of the most prevalent web vulnerabilities in the wild. It is devastating — a single injectable endpoint can lead to the exfiltration of an entire database, and often to code execution on the server behind it. And for anyone pursuing the certification, it is the single most-tested vulnerability in the CEH practical exam, where a large share of the web-section flags come from SQLi.

Two decades on, still breaching governments

It would be reasonable to assume a flaw this well-understood would be solved by now. It isn't. In January 2025, attackers exploited a SQL injection vulnerability in PostgreSQL (CVE-2025-1094) to breach BeyondTrust's Remote Support platform — and the intrusion chain ultimately reached the US Treasury Department. The underlying flaw was improper handling of user input in a database query: the very same class of bug that the "Bobby Tables" webcomic made famous twenty years earlier. That a single input-handling mistake could still, in 2025, form a link in a chain reaching a national treasury tells you everything about why this module matters. SQLi has sat at or near the top of the OWASP list for nearly the entire history of the project, and it continues to power major breaches today.

Where this sits in the web cluster

This module completes the three-part web cluster. Module 13 attacked the web server; Module 14 attacked the web application broadly and surveyed the whole injection family; this module drills into the one injection type that targets the database tier and deserves its own deep treatment. The connection to Module 14 is direct: everything you learned there about the injection root cause — untrusted input mixed with code — applies here, aimed specifically at SQL. If injection in general was the idea, SQLi is that idea followed all the way down to its most damaging conclusion.

What this module covers

We begin with fundamentals — how SQL and web applications interact, and exactly where and why injection becomes possible. Then the types of SQLi — the three channels (in-band, blind, out-of-band) and their techniques (union-based, error-based, boolean-based, time-based). Next, the detection and exploitation methodology — how a tester confirms a flaw, fingerprints the database, extracts data, and escalates. We cover the tools, centered on sqlmap alongside manual technique, and close with countermeasures, where a single defense — parameterized queries — stands above all others. Throughout, the emphasis is on understanding why each technique works, because that understanding is what separates someone who can run a tool from someone who can find and fix the flaws the tool misses.

Authorized targets only. SQL injection extracts real data from real databases, and running these techniques — especially automated tools like sqlmap — against any system you don't own or lack written authorization to test is a serious crime. Every technique in this module is for authorized engagements and deliberately-vulnerable practice apps: DVWA, OWASP Juice Shop, and the many purpose-built SQLi labs on platforms like TryHackMe, Hack The Box, and PortSwigger's Web Security Academy. 🧬 Fundamentals

How web apps talk to databases

To understand SQL injection, you first need to see how a normal web application uses a database. Most applications store their data — user accounts, products, orders, messages — in a relational database, and they retrieve it using SQL (Structured Query Language). When you log in, search, or view your account, the application builds a SQL query, sends it to the database, and displays the results. A login check might conceptually run a query like: find the user whose username and password match what was submitted. The database executes the query and returns matching rows. This is entirely normal and happens billions of times a day. The vulnerability arises not from using SQL, but from how the application builds these queries.

The fatal mistake: building queries by concatenation

SQL injection becomes possible when an application constructs its queries by concatenating user input directly into the query string. Imagine a login query built like this, in pseudocode:

query = "SELECT * FROM users WHERE username = '" + input_user + "' AND password = '" + input_pass + "'"

Here the application glues the user's input straight into the SQL text. If a user submits the username alice, the query works as intended. But the database receives one flat string of text and has no way to know which parts came from the developer and which came from the user — and that ambiguity is the entire vulnerability.

Escaping the value slot

Watch what happens when an attacker submits, as the username, the text ' OR '1'='1. Substituted into the query, the SQL becomes:

SELECT * FROM users WHERE username = '' OR '1'='1' AND password = '...'

The attacker's input included a single quote, which closed the string value the developer intended — and everything after it was then interpreted by the database as SQL code, not as data. The injected OR '1'='1' is always true, so the WHERE clause matches every row, and the login check is bypassed. The attacker's data escaped the value slot and became code. This is the essence of SQL injection: input that was supposed to be a mere value instead alters the structure and logic of the query itself.

The root cause, named

Step back and the root cause is exactly the one from the web applications module: the failure to keep code and data separate. By building the query through concatenation, the application mixed trusted code (the developer's SQL) with untrusted data (the user's input) into a single string, leaving the database no way to tell them apart. Every SQL injection — no matter how sophisticated — is a variation on this single mistake. This matters enormously for the countermeasures section, because it points directly at the fix: if the problem is that code and data got mixed, the solution is a mechanism that keeps them separate no matter what the user submits. Hold onto this framing; everything that follows is either an attacker exploiting this mixing, or a defender preventing it.

What an attacker can do once inside

Once a parameter is injectable, the consequences scale with the attacker's skill and the database's configuration. At minimum, they can bypass authentication, as above. Beyond that, they can read arbitrary data — dumping user tables, password hashes, personal information, and business data from anywhere in the database. They can often modify or delete data. On poorly-configured systems they may read or write files on the server, or even achieve command execution, turning a database flaw into full server compromise. And crucially, the database frequently holds exactly what an attacker wants most — credentials, payment data, personal records — which is why a single SQLi flaw so often becomes a headline breach. With the mechanism understood, we can now categorize the techniques by how the attacker gets the results back.

🗂️ Types of SQL Injection

Classified by how the data comes back

SQL injection is categorized not by the payload but by how the attacker receives the results — the channel through which data returns. This gives three families, and understanding which one applies to a given target determines which techniques you'll use. The three are in-band (results return through the same web channel you're attacking through), inferential or blind (no data returns directly, so you infer it from the application's behavior), and out-of-band (data is exfiltrated through a completely separate channel). CEH expects confident command of the first two families and their sub-techniques in particular.

In-band SQLi: results in the response

In-band injection is the easiest and fastest, because the data you extract comes back to you directly in the application's response. It has two main techniques:

🔗 Union-based

Uses the SQL UNION operator to append the attacker's own SELECT onto the original query, so the database returns a combined result set that includes data the attacker chose. A query displaying products can be made to also return usernames and password hashes from a users table. It requires matching the original query's column count and compatible data types — hence the tester first finds the column count (e.g. with ORDER BY), then places their data in the visible columns.

⚠️ Error-based

Deliberately provokes database error messages that leak information. When an application displays raw database errors, an attacker crafts input that forces the error text to contain the data they want — the database version, table names, or actual values. It's fast and informative, but depends on the application exposing errors (itself a misconfiguration).

A canonical union example, appended to an injectable id parameter:

?id=1 UNION SELECT username, password FROM users--

Blind (inferential) SQLi: reading the tea leaves

Often the application shows no query results and no error messages — but it is still injectable. Here the attacker extracts data indirectly, by asking true/false questions and observing how the application behaves. No data is ever returned directly; it is inferred. This is slower but every bit as effective, and it's where real skill shows.

✅ Boolean-based blind

The attacker injects a condition and watches whether the response changes — different content, length, or status code — depending on whether the condition is true or false. Comparing AND 1=1 (true) against AND 1=2 (false) confirms injectability; then, by asking questions like "is the first character of the admin password greater than 'M'?", the attacker bisects the character space and extracts data one character at a time.

⏱️ Time-based blind

When the response looks identical regardless of true or false, the attacker introduces a time delay as the observable signal. A payload like AND IF(1=1, SLEEP(5), 0) (MySQL) or WAITFOR DELAY '0:0:5' (MSSQL) makes the database pause only when the condition is true — so a 5-second delay means "true." Data is extracted the same bit-by-bit way, read from the clock.

The character-by-character extraction typically uses functions like ASCII(SUBSTRING(...)) to test individual characters — for example, AND ASCII(SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)) > 64. It's mechanical and slow by hand, which is exactly why automated tools shine here — but understanding the technique is what lets you recognize it, tune detection for it, and do it manually when a tool fails.

Out-of-band SQLi: a different exit

The third family, out-of-band (OOB) injection, is used when in-band and blind channels are impractical — for instance, when responses are too inconsistent to read reliably. Instead of returning data through the web response, the attacker makes the database itself send the data out through a different channel, most commonly by triggering a DNS or HTTP request to a server the attacker controls, with the stolen data encoded in the request. It depends on the database being able to make outbound network requests, so it's less universal, but it's a powerful fallback and a reminder that data can leave by paths other than the one it came in on. Its defense is the same as the others, plus restricting the database's outbound network access.

A tester's checklist

Experienced testers work these types in a reliable order, because the easy techniques confirm injectability fastest and the harder ones catch what the easy ones miss: error-based → union-based → boolean blind → time-based. A parameter that looks safe to a quick check may still be injectable via a blind technique, so the rule is to always test boolean and time-based payloads before concluding a parameter isn't vulnerable. This ordered checklist — run every time — is the difference between reliably finding SQLi and missing it. With the taxonomy in hand, the next section walks the full methodology from first probe to full extraction.

🎯 Detection & Exploitation

From first probe to full compromise

Exploiting SQL injection follows a clear progression, and knowing the sequence keeps testing efficient and thorough. It moves from confirming a flaw exists, to learning the database, to extracting its contents, to escalating as far as the configuration allows.

Step 1: Detection

The first task is finding an injectable input and confirming the vulnerability. Every place the application accepts input is a candidate: URL parameters, form fields, search boxes, HTTP headers, and cookies. The classic first probe is a single quote (') — if injecting one causes an error or a change in behavior, the input may be reaching a query unescaped. From there the tester applies the ordered checklist from the previous section: a quote to break the query, then boolean tests (AND 1=1 vs AND 1=2) to see if responses differ, then a time-based probe (SLEEP()) to catch cases where nothing visible changes. The golden rule bears repeating: test boolean and time-based payloads before concluding a parameter is safe, because blind injection hides from casual inspection.

Step 2: Fingerprint the database

Before extracting anything, the attacker must identify which database system they're facing — MySQL, PostgreSQL, Microsoft SQL Server, Oracle, or SQLite — because each uses different syntax. This step is easy to overlook and costly to skip: a payload written for MySQL may fail silently against PostgreSQL, making a genuinely vulnerable application look safe and leading the tester to a false negative. Fingerprinting is done by reading error messages, querying version functions (like @@version or version()), and noting behavioral quirks unique to each engine. Only once the DBMS is known can the tester choose payloads whose syntax will actually work — for extraction, string handling, and time delays all differ across engines.

Step 3: Extraction

With injectability confirmed and the DBMS known, the attacker enumerates and dumps the data. The usual path is to map the database structure first, then pull the valuable contents. Relational databases expose their own structure through metadata — most famously the information_schema views — which list the databases, tables, and columns present. The attacker queries these to discover, say, a users table with username and password columns, then extracts those columns' contents using whichever technique fits (union-based if results display, blind if not). The end result of a successful extraction can be the entire contents of the database: every account, hash, and record — which is why a single SQLi is so damaging.

Step 4: Escalation

The most severe SQLi goes beyond reading data. Depending on the database's privileges and configuration, an attacker may be able to read files from the server's filesystem (for instance, reading configuration files or credentials), write files (planting a web shell in the web root — connecting directly to the file-upload and web-shell attacks of Module 14), or in some cases achieve command execution on the underlying operating system (some databases expose features that run OS commands). Each of these turns a database vulnerability into a foothold on the server itself. This is why the impact of SQLi is capped not just by the flaw but by how the database is configured — a point that motivates the least-privilege countermeasure. This escalation potential is exactly why SQLi so often appears as the first link in an intrusion chain that ends deep inside a network — as the BeyondTrust-to-Treasury breach demonstrated.

Manual first, then automate

A note on practice that CEH emphasizes: the recommended workflow is to test manually first, then reach for automation. Manual testing builds the understanding to recognize what's happening and to handle cases tools stumble on; automated tools then handle the tedious, mechanical work — especially the character-by-character grind of blind extraction — at speed. The next section covers those tools, but the sequence matters: a tester who only knows the tool is lost when it fails, while one who understands the technique can always fall back to doing it by hand.

🛠️ Tools

sqlmap: the standard

One tool dominates SQL injection work: sqlmap, the open-source, industry-standard engine for automated SQLi detection and exploitation. It automates everything the previous section described — it detects injectable parameters, handles all the injection types (union, error, boolean, time, out-of-band), fingerprints the database engine, and extracts data automatically, from individual values up to the entire database. What would take hours of painstaking manual character-bisection in a blind injection, sqlmap does mechanically in minutes. It is the reason blind SQLi, though tedious by hand, is thoroughly practical in the real world.

# Point sqlmap at a URL parameter and let it detect + fingerprint sqlmap -u "https://target.example/item?id=1" # Feed it a saved raw request (picks up cookies, auth headers, POST body) sqlmap -r request.txt # Enumerate databases, then dump a table sqlmap -r request.txt --dbs sqlmap -r request.txt -D appdb -T users --dump

A practical tip testers rely on: feed sqlmap a raw request file with -r (saved from the browser or Burp) rather than retyping the URL, because it then automatically picks up cookies, authentication headers, and POST bodies — essential for anything behind a login.

Getting past WAFs

Many targets sit behind a Web Application Firewall that blocks obvious SQLi payloads. sqlmap addresses this with tamper scripts — over fifty of them — that transform payloads to evade WAF signatures: randomizing keyword case (UnIoN), inserting inline comments (/**/), encoding characters, and splitting keywords. The same evasion ideas apply in manual testing: case variation, comment insertion, double encoding, and HTTP parameter pollution are staple bypass techniques. But there's an important lesson embedded here — every one of these bypasses exists precisely because some team treated their WAF as the actual fix rather than as a secondary layer. The WAF is a speed bump, not a wall, a theme the countermeasures section returns to.

The supporting cast

🧰 Burp Suite

The web-testing proxy from Module 14 is central to SQLi work too: it captures the exact requests to save as sqlmap input, lets you manually craft and replay injection payloads in Repeater, and its scanner flags candidate injection points. Manual SQLi testing largely happens through Burp.

✍️ Manual technique

The most important "tool" is the tester's own understanding. Manual testing — a single quote, boolean pairs, a UNION crafted by hand — confirms and characterizes a flaw before automation, and is the only option when tools are blocked or behave unexpectedly. sqlmap is powerful, but it runs on the knowledge from the earlier sections.

The AI dimension

Reflecting CEH v13's modernization, AI assistants now feature in SQLi workflows too — the courseware demonstrates using tools like ShellGPT to generate payloads and drive testing from natural-language prompts, and AI is increasingly used to triage results and reason about complex, chained injections. There's also a sharp modern twist: AI-adjacent infrastructure has itself become a first-class SQLi target — a 2026 vulnerability in a popular LLM gateway (LiteLLM, CVE-2026-42208) was exploited within roughly a day of its advisory. The lesson is the one running through the whole course: AI accelerates the work on both sides, but it sits on top of the fundamentals. The tester who understands why an injection works can direct the AI, verify its output, and succeed where an unguided tool would fail.

sqlmap is not a toy. Because it automatically extracts real data and can modify databases, running sqlmap against any system without explicit written authorization is a serious crime. 🛡️ Countermeasures

One defense above all others

Most vulnerability classes are defended by a balanced set of controls. SQL injection is unusual: it has a single defense that actually solves the problem, with everything else serving only to limit damage when that defense is somehow absent. That defense is parameterized queries (also called prepared statements). Because the entire vulnerability comes from mixing code and data, and parameterized queries structurally prevent that mixing, they don't merely reduce SQLi risk — they eliminate the root cause. Understanding why is the most valuable takeaway in this module.

Parameterized queries: separating the channels

A parameterized query sends the SQL statement and the user's data to the database on separate channels. The application first defines the query with placeholders for the values:

-- The query structure is defined first, with a placeholder SELECT * FROM users WHERE username = ? AND password = ? -- The user's input is then bound to the placeholder, as data

The database pre-compiles the statement — fixing its structure — before the user's data is supplied. The data is then bound to the placeholders as pure values that can never change the query's structure. Now if an attacker submits ' OR '1'='1, that entire string is treated as a literal username to search for (and simply not found), rather than as SQL to execute. The parser sees code and data as separate inputs, so input can never be parsed as code — no matter what it contains. This is the fix the whole module builds toward, and it directly resolves the code-vs-data root cause identified in the fundamentals section.

The supporting layers

Parameterized queries are the fix; these layers limit the blast radius for the cases where, despite best intentions, the first layer fails or can't be applied everywhere.

✅ Allow-list input validation

Some query positions can't be parameterized — notably column and table names in ORDER BY clauses. For these, validate input against an allow-list of known-good values. Validation also adds a layer everywhere else, but it's a supplement to parameterization, never a substitute.

🔐 Least-privilege DB accounts

The application's database account should have only the permissions it needs — no more. If injection succeeds despite other controls, least privilege caps what the attacker can reach: no file access, no admin functions, no other databases. It bounds the damage rather than preventing the flaw.

🧱 WAF as an alarm

A Web Application Firewall blocks known injection patterns and buys time, but as the tools section showed, dozens of documented bypasses exist. Treat the WAF as an alarm and speed bump, never as the solution — every bypass exists because someone relied on it as the fix.

🕵️ Detection & monitoring

Log and alert on the signatures of active exploitation: UNION SELECT, SLEEP(, WAITFOR DELAY, and information_schema appearing in parameters; enable slow-query logging to catch time-based blind injection. Correlated with unusual data-access patterns, these signals catch attacks that slip past prevention.

A note on stored procedures and encryption

Two common misconceptions are worth correcting. First, stored procedures are not automatically a defense — a stored procedure that itself builds queries by concatenation is just as injectable. Only parameterized calls combined with procedures that use parameterized internal queries are safe; the protection comes from parameterization, not from the procedure wrapper. Second, defense in depth extends to the data itself: column-level encryption of the most sensitive fields means that if a UNION-based dump does succeed against a hardened-but-still-vulnerable app, the attacker leaves with ciphertext rather than usable data. Neither replaces parameterization, but both reflect the mature mindset of assuming any single control can fail.

The through-line

SQL injection is, in the end, a remarkably clean illustration of the deepest principle in web security: keep code and data separate, and never trust input. The vulnerability is that principle violated by query concatenation; the definitive fix is that principle enforced by parameterized queries; and the supporting layers — validation, least privilege, WAF, monitoring, encryption — exist to contain the damage on the day the principle is accidentally broken somewhere in a large codebase. That a flaw this well-understood still breaches governments in 2025 is not a failure of knowledge but of consistent application — parameterization everywhere, without exception. This module completes the web cluster; an ethical hacker who has internalized these three modules can assess a web system from the server, through the application, down to the database, and help build one that holds.

The through-line

SQL injection has many faces — union, error, boolean, time, out-of-band — but one root cause and one primary fix. The root cause is the failure to separate code from data; the fix is parameterized queries, which put user input in a channel the database never parses as SQL, defeating every family at once. Least privilege contains what slips through, suppressed errors and restricted egress close secondary channels, and a WAF buys time — but the real fix lives in the code, applied everywhere untrusted input meets a query.
