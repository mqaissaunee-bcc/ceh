CEH v13 Module 11: Session Hijacking

Session Hijacking

Taking over an authenticated session to impersonate a user without their credentials: application-level token theft, network-level TCP hijacking, the modern token-theft economy that bypasses MFA, and the session-management controls that defend against it.

⏱️ 3+ hours 🧪 Hands-on labs 📝 Assessment 🔬 Interactive demos

🎫 Overview

Stealing the session, not the password

Session hijacking is the theft and unauthorized use of a legitimate user's active session — taking over a connection that has already been authenticated, so the attacker can impersonate the user without ever knowing their password. This is the crucial idea that makes the whole module click: the attacker doesn't break in through the front door by guessing credentials; they slip in through a door the legitimate user already opened and walked through. Once a user has logged in, the system trusts their session; hijack that session and you inherit that trust wholesale.

This distinction matters enormously. Every authentication defense an organization deploys — strong passwords, password policies, even multi-factor authentication — protects the login. Session hijacking sidesteps all of it by attacking what comes after the login. It is, in a sense, the attack that renders the front-door defenses irrelevant, which is exactly why it has become one of the most important and fastest-growing threats in modern security.

Why this is the attack that bypasses MFA

The single most important consequence to understand is that session hijacking defeats multi-factor authentication. Here is the logic, and it is worth internalizing: authentication and the session are two separate phases. First the user proves who they are — password, then MFA code, biometric, whatever the application requires. Only after that succeeds does the application issue a session token (a cookie or similar) that says "this browser is now the authenticated user." From that moment, every request simply presents the token; the hard authentication is never repeated.

So a stolen session token is a post-authentication bearer credential — whoever holds it is already "logged in." Replaying it requires no password and no MFA, because those checks already happened. This is why session hijacking has surged: as MFA adoption has made credential theft less useful, attackers have shifted to stealing the one thing that renders MFA moot — the session token itself. Industry reporting describes it as one of the fastest-growing attack vectors, with year-over-year increases well into the triple digits, precisely because it is the clean way around the authentication controls organizations have invested so heavily in.

Two layers, two families of attack

Session hijacking happens at two different layers of the stack, and CEH organizes the module around this division. Understanding which layer an attack targets tells you both how it works and how to defend against it.

🍪 Application-level hijacking

Attacks the session token that a web application uses to track a logged-in user — stealing the cookie or token via cross-site scripting, forcing a known one via session fixation, or guessing a weak one. This is where most modern session hijacking lives, because the web is where sessions matter most.

🌐 Network-level hijacking

Attacks the underlying TCP connection itself — predicting sequence numbers to inject packets into an established session, or sitting in the middle of the traffic via a man-in-the-middle position. Lower-level and more classic, targeting the transport rather than the application.

The two share a goal — take over an active session — but attack different things: application-level goes after the token the app trusts, network-level goes after the connection the token travels over.

What this module covers

We begin with session fundamentals — how sessions and tokens actually work, since you can't attack or defend what you don't understand. Then we examine the two families in turn: application-level hijacking (token theft via XSS, session fixation, predictable tokens, and the modern infostealer economy) and network-level hijacking (TCP sequence prediction, MITM, blind hijacking, and IP spoofing). We survey the tools — Burp Suite chief among them — and close with the countermeasures that make sessions hard to steal and stolen sessions hard to use. Session hijacking ties together threads from across the course: the sniffing of Module 8 (capturing tokens), the malware of Module 7 (infostealers), the social engineering of Module 9 (AiTM phishing), and the web attacks still to come — making it a natural hub in the curriculum.

Session hijacking is unauthorized access, full stop. Taking over another person's session — even to demonstrate a flaw — means accessing systems and data as someone you are not, which is illegal without explicit authorization. These techniques are taught so you can test session management under a sanctioned engagement and help organizations fix it. Practice only in labs and authorized scopes.

🔑 Session Fundamentals

The problem sessions solve

To understand session hijacking, you first have to understand why sessions exist at all — and the answer is a fundamental limitation of the web. HTTP is stateless: each request a browser sends is, as far as the protocol is concerned, an independent event with no memory of what came before. The server has no built-in way to know that the request arriving now is from the same user who logged in a moment ago. Every request, technically, is a stranger knocking at the door. This is a problem, because a logged-in experience requires the server to remember who you are across many requests.

Sessions are the solution. After a user authenticates, the server creates a session — a record that "this user is logged in" — and issues the browser a unique session identifier (a session ID or token). The browser presents that identifier on every subsequent request, and the server uses it to look up the session and recognize the user. The token becomes a stand-in for the full authentication: instead of asking for the password on every click, the server just checks the token. That efficiency is essential to a usable web — and it is exactly the mechanism session hijacking exploits.

Cookies and tokens

The session identifier has to be stored somewhere in the browser and sent with each request. The classic mechanism is the cookie — a small piece of data the server sets in the browser, which the browser automatically returns on every subsequent request to that site. When you log into a web application, the server's response includes a session cookie, and from then on your browser silently attaches it to everything you send. Modern applications may use other forms — JWTs (JSON Web Tokens), opaque tokens, or OAuth access and refresh tokens — but the principle is identical: a piece of data that proves "I am the authenticated session."

Two token types deserve special note because they are the highest-value targets. OAuth and refresh tokens function as bearer tokens — whoever possesses them gains access — and refresh tokens are the "crown jewels" of session theft, because they can be used to obtain fresh access tokens indefinitely, renewing access long after the original session should have expired. This is why the security of these tokens matters so much: they are, functionally, a portable copy of the user's authenticated identity.

The TCP session underneath

Beneath the application's cookie-based session sits a lower-level session: the TCP connection that actually carries the traffic. Recall from the scanning module that a TCP connection begins with the three-way handshake (SYN → SYN-ACK → ACK), whose purpose is to synchronize sequence numbers between client and server. Once synchronized, the two sides exchange data, each packet carrying a sequence number so the receiver can order them correctly and detect anything out of place.

Critically, a TCP session is identified by a 4-tuple: the client IP address, client port, server IP address, and server port. Any packet arriving with that quadruple is treated as belonging to the session. This is the seam that network-level hijacking exploits: an attacker who can spoof those four values and predict the correct next sequence number can inject packets that the receiver accepts as coming from the legitimate partner. The sequence numbers are the session's only real defense against injected packets — which is why modern operating systems randomize them, and why sequence prediction is the heart of TCP session hijacking.

Two sessions, two attack surfaces

The key takeaway that frames the rest of the module: there are really two sessions layered on top of each other, and each is a target. At the application layer, the session is the cookie or token the web app trusts — steal it and the app thinks you are the user. At the network/transport layer, the session is the TCP connection carrying the traffic — hijack it and you inject yourself into the live conversation. The next two sections take these in turn. Both are session hijacking; they simply attack the session at different depths, and — as we'll see — the application-layer attacks dominate the modern threat landscape because that is where the valuable, long-lived, MFA-bypassing tokens live.

🍪 Application-Level Hijacking

Going after the token the application trusts

Application-level session hijacking targets the session identifier a web application uses to recognize a logged-in user. The goal is simple and consistent across every technique here: get hold of a valid session token, then present it as your own. Once an attacker has the victim's session cookie, they load it into their own browser and are instantly logged in as the victim — no password, no MFA, as if they had walked in wearing the user's identity. As one practitioner memorably put it, stealing a session cookie and pasting it into your browser feels like finding a master key card that opens every door in the building. This is where the vast majority of modern session hijacking happens, because web sessions are where the valuable, MFA-bypassing tokens live.

How tokens get stolen

There are several routes to a victim's token, and knowing them is knowing this attack. Each maps to a defense covered later.

💉 Cross-site scripting (XSS)

The attacker injects malicious JavaScript into a vulnerable web page; when the victim loads it, the script runs in their browser and exfiltrates the session cookie to an attacker server. The classic web-based theft — defeated by the HttpOnly cookie flag, which hides the cookie from JavaScript. (XSS is covered in depth in the web-application module.)

🦠 Infostealer malware

The dominant technique of 2025–2026. Malware on the victim's device silently reads every cookie from the browser's storage and exfiltrates them in bulk. Families like LummaC2, RedLine, Raccoon, and Vidar are purpose-built for this, harvesting corporate SSO, cloud consoles, SaaS, and email sessions within minutes of infection.

🎣 Adversary-in-the-middle (AiTM)

A phishing proxy sits between the victim and the real site. The victim enters credentials and completes MFA against the real service through the proxy, which captures the resulting session token. This is the technique that specifically defeats MFA, and it accounts for a large share of modern phishing.

📡 Network sniffing (sidejacking)

Capturing session tokens off the wire on an unencrypted connection. Once trivial with tools like FireSheep on open Wi-Fi, it is now largely obsolete thanks to ubiquitous TLS — a rare security success story, and a reminder of why HTTPS-everywhere matters.

Manipulating the session, not just stealing it

Beyond outright theft, two techniques manipulate the session mechanism itself. Session fixation is a clever inversion: instead of stealing the victim's token after login, the attacker forces a token they already know onto the victim before login. The victim then authenticates using that fixed session ID — and because the attacker already knows it, they now hold an authenticated session. The defense is a one-line rule every framework should follow: regenerate the session ID immediately after every successful login, so any pre-login token becomes worthless.

Predictable tokens are the other flaw. If an application generates session IDs in a guessable way — sequentially, or from a weak algorithm — an attacker can simply predict or brute-force a valid one belonging to another user, no theft required. This is why session tokens must be long, random, and cryptographically unpredictable; a token an attacker can guess is a session an attacker can steal without ever touching the victim.

Why stolen tokens are so dangerous

Two properties make application-level hijacking especially potent. First, the theft is often invisible and delayed: an infostealer harvests a token today, but the attacker may not replay it for days or weeks, and when they do, the request carries a perfectly valid token — nothing obviously wrong to detect. Stolen cookies surface on dark-web marketplaces and Telegram channels within a day or two of theft, decoupling the compromise from its use. Second, hijacked sessions enable lateral movement across SaaS: a single stolen SSO or cloud token can grant access to many connected applications, letting the attacker ride trusted connections from one compromised app into others. A stolen session is rarely the end of an attack — it is a foothold that opens onto everything the user could reach.

🌐 Network-Level Hijacking

Hijacking the connection itself

Where application-level hijacking steals the token a web app trusts, network-level hijacking attacks the TCP connection underneath — the transport-layer session carrying the traffic. Rather than obtaining a cookie and replaying it later, the attacker inserts themselves into a live connection, injecting packets that the endpoints accept as part of the ongoing conversation. This is the more classic, lower-level form of session hijacking, and while it is less dominant today than token theft (TLS encryption has blunted much of it), it remains fundamental to understanding how sessions can be subverted at the network layer — and it is tested heavily on the CEH exam.

TCP session hijacking and sequence prediction

Recall the fundamentals: a TCP session is identified by the 4-tuple (client IP, client port, server IP, server port), and its packets carry sequence numbers that keep the conversation ordered. TCP session hijacking exploits exactly this. To take over an established session, the attacker must do two things: desynchronize the legitimate parties and inject their own packets in a way the receiver accepts.

The linchpin is sequence-number prediction. If the attacker can correctly guess the next sequence number the server expects, and spoof the victim's IP address, they can inject a packet that the server processes as if it came from the legitimate client. The real client's subsequent packet then arrives with a sequence number the server sees as a duplicate and ignores — the attacker has stepped into the conversation. This is why sequence numbers are the session's real defense at this layer, and why modern operating systems generate them with strong randomization: predictable sequence numbers (common in older systems) made this attack far easier than it is today.

Blind hijacking and IP spoofing

A key variable is whether the attacker can see the traffic. When the attacker is positioned to observe the session's packets, they can read sequence numbers directly and hijack with precision. When they cannot — when they are injecting blind — they must guess the sequence numbers without feedback, and they send commands without seeing the responses. Blind hijacking is harder and less reliable, but still dangerous: an attacker can inject a command (say, adding a user or changing a setting) even without observing the results, as long as their spoofed, correctly-sequenced packet lands. Both forms rely on IP spoofing — forging the source address so packets appear to come from the legitimate participant, which is what makes the injected traffic acceptable to the target in the first place.

Man-in-the-middle: the commanding position

The most powerful network-level position is the man-in-the-middle (MITM), where the attacker sits directly in the path between client and server, seeing and relaying all traffic. From this position, hijacking is straightforward — the attacker observes everything, including sequence numbers and (if unencrypted) session tokens, and can read, modify, inject, or drop traffic at will. On a local network, the classic route to a MITM position is ARP poisoning (from the sniffing module), which tricks the victim and gateway into sending their traffic through the attacker. MITM connects the two families of this module: from the middle, an attacker can hijack the TCP session directly and harvest application tokens from the traffic flowing past. It is why the single most important network-level countermeasure — end-to-end encryption with TLS — is so decisive: even a perfectly-positioned MITM sees only ciphertext, unable to read tokens or meaningfully inject into the protected stream.

Why network-level hijacking has declined

It is worth being honest about the modern reality: pervasive TLS encryption has made network-level hijacking much harder than it once was. When every session is encrypted end to end, sniffing yields gibberish, injected packets fail integrity checks, and a MITM sees only ciphertext. This is a genuine defensive success, and it explains why attackers have largely shifted to the application-level token theft of the previous section — stealing the token from the endpoint (via malware or phishing) rather than fighting the encrypted transport. Still, the concepts here remain essential: they explain why encryption matters so much, they apply wherever encryption is missing or downgraded, and they underpin the countermeasures that close the module.

🛠️ Tools

Tools across the two layers

Because session hijacking spans the application and network layers, its tooling does too — some tools inspect and manipulate web sessions, others craft and intercept network traffic. Many of these tools have already appeared in earlier modules, which reflects how session hijacking sits at the crossroads of the curriculum: it draws on web-testing proxies, sniffers, and MITM frameworks alike. As always, the professional's skill is knowing which tool answers the question at hand.

Application-layer tooling

🧰 Burp Suite

The standard web-application testing proxy and the central tool for this module. It intercepts requests between browser and server, letting a tester inspect session cookies and tokens, test whether the Secure/HttpOnly/SameSite flags are set, check whether tokens are regenerated after login (session fixation), and assess token randomness. The go-to for auditing an application's session management.

🔎 Browser developer tools

Even the browser's built-in dev tools reveal a great deal — the cookies set, their flags, and their values. A first-pass check of an application's session hygiene often starts here, confirming whether session cookies carry the protective flags before deeper testing with Burp.

Network-layer tooling

🦈 Wireshark

The packet analyzer from the sniffing module. In session-hijacking work it is used to observe TCP sequence numbers, examine the session's 4-tuple, and — on any unencrypted traffic — spot tokens in the clear. Essential for understanding what a network-level attacker can and cannot see.

🎭 Ettercap / Bettercap

MITM frameworks that automate ARP poisoning and traffic interception, placing the attacker in the middle of a local-network conversation. They operationalize the man-in-the-middle position that makes network-level hijacking possible.

🔧 Packet crafters (hping3, Scapy)

Tools for building custom TCP packets by hand — used to craft the spoofed, correctly-sequenced packets that a network-level hijack injects. They give the fine-grained control needed to demonstrate sequence-prediction attacks in a lab.

🕰️ FireSheep (historical)

Worth knowing as history: the 2010 tool that made sidejacking on open Wi-Fi trivially easy, capturing unencrypted session cookies with a click. It was influential precisely because it shocked the industry into adopting HTTPS everywhere — the defense that made it obsolete.

The modern reality of tooling

One honest observation ties the toolkit to the current threat landscape. Because TLS has largely closed off network-level sniffing and injection, the "tool" behind most real session hijacking today is not a network utility at all — it is infostealer malware harvesting cookies from the endpoint, and phishing kits (AiTM proxies) capturing tokens during login. The center of gravity has moved from crafting packets on the wire to stealing tokens from the browser. This is why the defenses in the next section emphasize endpoint hygiene and token protection as much as network encryption: the tools that matter most now operate on the victim's device, not on the network path.

Practice safely. Session-hijacking techniques should be exercised only against systems you own or are authorized to test. TryHackMe and Hack The Box offer labs — including the classic "steal a cookie via XSS and log in as admin" exercise — where these skills can be built legally.

🛡️ Countermeasures

Two goals: make tokens hard to steal, and stolen tokens hard to use

Defending against session hijacking has two complementary aims. The first is prevention — making it difficult for an attacker to obtain a valid session token in the first place. The second, increasingly important, is containment and detection — ensuring that even a stolen token is hard to use and that its misuse is caught quickly. This second aim matters because of a hard truth from earlier in the module: a valid stolen token looks legitimate, so no defense makes theft impossible, and the mature approach assumes some tokens will be stolen and limits the damage.

Encrypt everything

The foundational countermeasure — the one that single-handedly retired an entire class of attacks — is HTTPS/TLS everywhere. Encrypting all traffic end to end means an attacker sniffing the network sees only ciphertext, unable to read session tokens off the wire or meaningfully inject into the stream. This is what made sidejacking obsolete and what neutralizes even a well-positioned man-in-the-middle. Encryption should be enforced, not optional: HSTS (HTTP Strict Transport Security) tells browsers to only ever connect over HTTPS, defeating downgrade attacks that try to force traffic back to unencrypted HTTP. For the highest-security environments, mutual TLS (mTLS) requires the client to present a certificate too, so a stolen token alone is not enough — the attacker would also need the device's certificate.

Harden the session token

The token itself must be built and handled to resist theft and misuse. Several controls work together:

🎲 Strong, random tokens

Session IDs must be long and cryptographically unpredictable, so they cannot be guessed or brute-forced. This closes the predictable-token attack entirely.

🔄 Regenerate after login

Issue a brand-new session ID immediately after every successful authentication. This is the definitive defense against session fixation — any token the victim carried before login becomes worthless.

🚩 Secure cookie flags

Set HttpOnly (hides the cookie from JavaScript, blocking XSS theft), Secure (sends it only over HTTPS), and SameSite (limits cross-site sending, reducing CSRF-driven attacks). These three flags are the baseline of cookie hygiene.

⏱️ Short timeouts

Expire sessions after brief inactivity and require re-authentication for high-privilege actions regardless of session age. A short lifetime shrinks the window in which a stolen token is useful.

Bind the session, and detect the anomalies

The most important modern additions address the reality that tokens do get stolen. Session binding ties a token to contextual properties of the legitimate client — device fingerprint, browser signature, IP address (allowing for NAT) — so that when a stolen token is replayed from a different environment, the mismatch is detectable and the session can be rejected. This directly counters the infostealer-and-replay pattern that dominates today, where the attacker uses the token from their own machine.

And because a valid token presented by an attacker is, by definition, hard to distinguish from legitimate use, behavioral anomaly detection becomes the last and essential line: monitoring for the tell-tale signs that the human behind a token has changed — a sudden new location or device, impossible travel, unusual access patterns, activity from a data-center IP. Contextual, continuous evaluation of a session catches hijacking after the initial theft, which static, login-focused controls miss entirely. This is why the strongest defense is described as behavioral and contextual rather than purely preventive.

Defense in depth — and the endpoint

No single control suffices; together they form a resilient defense. TLS and HSTS deny the network attacker. Strong random tokens defeat guessing. Regeneration defeats fixation. The cookie flags defeat XSS theft and downgrade. Short timeouts and session binding shrink the value of a stolen token, and anomaly detection catches replay when it happens. But the modern threat adds one more front: because infostealer malware is now the leading token-theft method, endpoint security — detecting the credential-dumping behavior of stealers before they exfiltrate the browser's cookies — is now central to session-hijacking defense, tying this module back to the malware defenses of Module 7. The unifying lesson: authentication protects the door, but the session is what the attacker is really after, so protecting the session — in transit, in the browser, and in use — is what actually keeps the user's identity theirs. With sessions understood, the course turns next to the defenses attackers must evade and the web systems they target most.
