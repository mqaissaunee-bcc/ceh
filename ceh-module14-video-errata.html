Corrections for the “Hacking Web Apps” video

Read this after you watch the video. The video is accurate overall, but a few statements need clarifying and several topics are missing. Where the video and Module 14 disagree, go with the module.

Clarifications

Nothing in the video is flatly wrong, but these statements could mislead you.

11:17

Parameterized queries do not stop every injection attack

The video says

“To defeat injection attacks once and for all, you use parameterized queries.”

What’s correct

Parameterized queries stop SQL injection. Command injection needs safe APIs that don’t invoke a shell. XSS needs output encoding. The idea that covers all of them is the principle behind these: keep code and data separate.

Read more: Injection & XSS → “The unifying defense”

8:26

Credential stuffing and weak passwords are separate problems

The video says

Weak password policies leave you “wide open to credential stuffing.”

What’s correct

Credential stuffing replays passwords leaked from other breaches, so it works even against strong passwords if people reuse them. The module lists weak password policies, credential stuffing, brute force and flawed or missing MFA as separate authentication failures. The video never mentions MFA, which is one of the main defenses.

Read more: Access & Authentication → “Authentication and session failures”

11:51

The module’s summary has five ideas, not two

The video says

Almost everything “boils down to two fundamental root causes”: mixing code with data, and trusting the client.

What’s correct

The module’s through-line has five ideas:

  1. Don’t trust the client.
  2. Keep code and data separate.
  3. Enforce access on the server.
  4. Handle identity and sessions properly.
  5. Build security in throughout the lifecycle.

Read more: Countermeasures → “The through-line”

Not in the video

The module covers these topics and the video skips them. Read them in the module before the knowledge check.

The full OWASP Top 10 (2025)

The video names four categories and never shows the list. Learn all ten, with their numbers:

  1. A01 Broken Access Control
  2. A02 Security Misconfiguration
  3. A03 Software Supply Chain Failures
  4. A04 Cryptographic Failures
  5. A05 Injection (SQL injection, XSS and command injection all belong here)
  6. A06 Insecure Design
  7. A07 Authentication Failures
  8. A08 Software or Data Integrity Failures
  9. A09 Security Logging & Alerting Failures
  10. A10 Mishandling of Exceptional Conditions

In 2025, A01 also absorbed SSRF and API authorization failures. The Top 10 is not a checklist or a compliance standard.

Read: The OWASP Top 10 → “The OWASP Top 10 (2025)”

API weaknesses

APIs are one of the most attacked parts of a modern application, and their inputs are often under-tested. Know two terms: BOLA (broken object-level authorization) and BFLA (broken function-level authorization). Both now sit inside A01. Authenticate and authorize every endpoint and validate every parameter.

Read: Access & Authentication → “File upload and API weaknesses”

The reinforcing layers of defense

The video stops at secure coding. The module adds four layers on top:

  • A Web Application Firewall (WAF), which blocks known attack patterns and gives virtual patching. It is a layer, never a substitute for fixing the code.
  • Security response headers: Content-Security-Policy, HSTS, X-Content-Type-Options.
  • Logging and alerting (A09), so attacks are noticed in time.
  • Regular penetration testing and code review.

Read: Countermeasures → “Reinforcing layers”

XSS: an example and its defenses

A reflected XSS test looks like <script>alert(document.cookie)</script> typed into a search box. The defense is context-appropriate output encoding, backed up by a Content-Security-Policy and the HttpOnly cookie flag.

Read: Injection & XSS → “Cross-Site Scripting (XSS)”

Access control, sessions and file upload details

  • Forced browsing (on the slide, not explained): reaching a restricted page directly by its URL because the app only hid the link.
  • The access control defense includes deny by default.
  • Session fixation: the token is not regenerated after login. Cookies also need the Secure flag.
  • File uploads: besides checking content, rename uploaded files, store them outside the web root, and never execute them.

Read: Access & Authentication → “Broken access control” through “File upload and API weaknesses”

More on the tools

  • Burp Suite’s four parts: Proxy, Repeater, Intruder and Scanner.
  • OWASP ZAP is a DAST tool too, like Burp.
  • Other names to know: Semgrep and Checkmarx (SAST), OWASP Dependency-Check (SCA), Gobuster, dirb and Nikto (discovery).
  • Practice legally on DVWA, OWASP Juice Shop and WebGoat.
