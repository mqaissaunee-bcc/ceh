Errata for the “Hacking Web Apps” video

The 13:13 explainer video was checked line by line against Module 14, which is the authoritative source. Where the two disagree, the module is right. No outright factual errors were found. This page lists 27 items: 7 imprecise or unsupported statements, 18 omissions and 2 slide defects.

What to know before assigning the video

The video is accurate. It follows the module’s structure and explains the architecture, the “never trust the client” principle, the four-step methodology, XSS, command injection, IDOR and the intercepting proxy correctly. Its weakness is what it leaves out. Four things need attention.

  1. Item 5: the OWASP Top 10 is never listed. Only four of the ten categories are named, and the numbers A05 and A07 are never spoken, although the video has a section on each.
  2. Item 18: API weaknesses, including BOLA and BFLA, are absent.
  3. Item 24 and item 16: the video never mentions a WAF, security response headers, logging and alerting, or MFA.
  4. Item 25: the closing review reduces the module’s five unifying ideas to “two fundamental root causes.”

Introduction and roadmap 0:00–0:53

#1 0:10–0:33 ∅ Omission Narration

Module map and legal warning are cut short

In the video

The introduction contrasts the server platform with the application layer. The only authorization reminder is the sign-off at 13:06: “keep practicing on authorized targets.”

In the module

Overview → “Keeping the layers straight”: Module 13 is the server, Module 14 the application, and Module 15 gives SQL injection its own treatment. The Overview also warns that testing an application you don’t own, without written permission, is illegal, and names the practice targets: DVWA, OWASP Juice Shop, WebGoat, and the labs on TryHackMe and Hack The Box.

Correction

Add the three-module map and the written-permission warning near the start, and name the practice targets. The video never mentions any of them.

Section 1: Architecture and methodology 0:53–3:18

#2 1:07–1:17 ≈ Imprecise Narration

Fixing a web server made to sound trivial

In the video

For a web server, “if a vulnerability is discovered there, you just look up a patch and apply it. Boom, done.”

In the module

The Overview says a web server is “a known product with known vulnerabilities you can look up.” It does not say fixing one is effortless, and Module 13 teaches that half of web server compromise is misconfiguration, which is fixed by hardening rather than patching.

Correction

Keep the contrast (known product versus bespoke code) but drop “boom, done.” It undercuts what students just learned in Module 13.

#3 1:17–1:46 ∅ Omission Narration

APIs mentioned in passing, not as an attack surface

In the video

The three tiers are named, “communicating via HTTP requests and structured APIs.”

In the module

Architecture → “How a web application is built”: the client is increasingly a single-page application; APIs are often REST or GraphQL; and “every tier and boundary is an attack surface.” APIs are called “one of the most attacked surfaces of all,” because API parameter inputs are frequently under-tested.

Correction

Add the point that APIs are a heavily attacked, under-tested surface. It sets up the API weaknesses topic that the video also leaves out (see Section 4).

#4 2:44 ∅ Omission Narration and slide

Form fields missing from the list of inputs

In the video

Entry points listed: URL parameters, headers, cookies, file uploads, APIs. The slide shows the same five.

In the module

The testing methodology lists six: URL parameters, form fields, headers, cookies, file uploads and API endpoints. The testing step probes them “for the vulnerability classes in the OWASP Top 10.”

Correction

Minor. Add form fields to the narration and the slide.

Section 2: The OWASP Top 10 3:18–4:43

#5 3:18–4:43 ∅ Omission Narration and slide

The Top 10 list is never shown or read out

In the video

Four of the ten categories are named: Broken Access Control (the only one given its number, A01), Security Misconfiguration, Software Supply Chain Failures and Mishandling of Exceptional Conditions. No slide lists the ten.

In the module

The OWASP Top 10 (2025), in ranked order: A01 Broken Access Control; A02 Security Misconfiguration; A03 Software Supply Chain Failures; A04 Cryptographic Failures; A05 Injection; A06 Insecure Design; A07 Authentication Failures; A08 Software or Data Integrity Failures; A09 Security Logging & Alerting Failures; A10 Mishandling of Exceptional Conditions. The module also notes that Injection fell from #3, that A09 was renamed, and that the trend is “away from symptoms and toward root causes,” with Injection the last symptom category.

Correction

This is the largest gap. Add a slide with all ten. The video’s own sections on injection and authentication never say “A05” or “A07,” and knowledge check question 5 asks which category SQL injection, XSS and command injection belong to.

#6 3:25 ∅ Omission Narration

What the Top 10 is, and is not

In the video

The list is “the security industry’s most widely cited standard,” ranking risks “based on massive amounts of real world data.”

In the module

It is compiled from real-world testing data, reported CVEs and community input. It is “not a checklist of every possible bug, nor a compliance standard.” The 2025 edition was unveiled at OWASP’s Global AppSec conference in November 2025, and an assessment framed around an outdated list misses the shifts.

Correction

Add that it is not a compliance standard, and give the release date.

#7 3:40–4:00 ∅ Omission Narration

A01’s 2025 expansion not mentioned

In the video

Broken Access Control “firmly holds the number one spot” because it is contextual.

In the module

A01 “now absorbs SSRF and explicitly covers API authorization failures (BOLA/BFLA).” The knowledge check explanation for question 2 repeats this.

Correction

Add one sentence. The video does list SSRF under broken access control at 8:07, but never says that placement is new in 2025.

#8 4:09–4:17 ≈ Imprecise Narration

Different reason given for misconfiguration’s rise

In the video

Misconfiguration rose because teams deploy continuously “but sometimes they’re failing to maintain secure default settings.”

In the module

“Teams deploy continuously but scan intermittently, leaving exposure windows.” The module also says it is up from #5 and that essentially all tested applications show some form of it.

Correction

Use the module’s explanation: the gap is between continuous deployment and intermittent scanning. Add that it moved up from #5.

Section 3: Injection and XSS 4:43–7:16

#9 5:29–6:23 ∅ Omission Narration

XSS has no example, no category and no defense at this point

In the video

XSS is defined and its three forms are described accurately.

In the module

The XSS section gives a reflected example, <script>alert(document.cookie)</script>, and states the defense: context-appropriate output encoding, “reinforced by a Content-Security-Policy and the HttpOnly cookie flag from Module 11.” XSS sits inside Injection (A05). The injected script can also “take actions as the victim,” and DOM-based XSS is increasingly common in single-page apps. The injection family also includes LDAP and NoSQL injection.

Correction

Add the example payload and say XSS is part of A05. Output encoding appears later (11:26) and HttpOnly at 8:43, but Content-Security-Policy is never mentioned in the video.

#10 6:23–7:07 ∅ Omission Narration

No defense given for command injection

In the video

The ping example is explained well, ending with a web shell and “full system compromise.”

In the module

“Never pass untrusted input to an interpreter; use safe APIs that don’t invoke a shell; and validate input strictly.”

Correction

Add the defense. “Safe APIs” is never said anywhere in the video, and the knowledge check explanations for questions 6 and 10 both use it.

#11 6:25–7:10 ▣ Slide defect Slide

In the video

The injected command 8.8.8.8; cat /etc/passwd is shown correctly, but the output beneath it is invented text: malformed ping lines and near-identical “daemon” rows that do not resemble a real /etc/passwd.

In the module

The module gives the input and says the attacker “may get both the ping and the contents of the password file.”

#12 6:43 ≈ Imprecise Narration

File name spoken as “/etc/password”

In the video

In the module

The module’s example is 8.8.8.8; cat /etc/passwd, which the slide shows correctly.

Section 4: Access and authentication 7:16–9:10

#13 7:16 ▣ Slide defect Slide

Section title card asks only “Who are you?”

In the video

The card for “Access & Auth” carries the subtitle “Who are you?” The faint background art on the definition slides (0:55 and 9:15) also reads “Broken Authentication,” the older category name.

In the module

Access & Authentication poses two questions: who are you? (authentication) and what are you allowed to do? (authorization). The second is the #1 risk. The 2025 category is named “Authentication Failures.”

Correction

Cosmetic. The narration at 7:29 asks both questions correctly.

#14 7:38–8:21 ∅ Omission Narration and slide

Forced browsing is on the slide but never explained; “deny by default” is missing

In the video

IDOR, privilege escalation and SSRF are narrated. “Forced Browsing: Accessing hidden URLs” appears on the slide only.

In the module

Forced browsing is reaching restricted pages directly by URL when the app “only hides them from the interface rather than actually enforcing access on the server.” SSRF targets internal systems “or cloud metadata.” The defense is to enforce authorization on the server for every request, deny by default, and verify ownership and role.

Correction

Narrate forced browsing, mention cloud metadata, and add “deny by default,” which the video never says.

#15 8:26 ≈ Imprecise Narration

Credential stuffing tied to weak password policies

In the video

“If you have weak password policies, you’re wide open to credential stuffing, where attackers just reuse passwords leaked from other breaches.”

In the module

Authentication failures “include weak password policies, vulnerability to credential stuffing (replaying credentials leaked from other breaches) and brute force, flawed or missing MFA.” These are listed as separate failures.

Correction

Present them as separate problems. The definition of credential stuffing is correct; the cause-and-effect link is the video’s own.

Beyond the module text. Credential stuffing replays passwords that are already valid, so a strict password policy does not stop it. Password reuse and missing MFA are what expose an application.

#16 8:26–8:50 ∅ Omission Narration

MFA, brute force and session fixation left out

In the video

Covered: credential stuffing, predictable tokens, sessions that never expire, and the HttpOnly and SameSite flags.

In the module

Also listed: brute force; flawed or missing MFA; tokens not regenerated after login (session fixation); and the Secure flag alongside HttpOnly and SameSite. The section ties all of this to Module 11 (session hijacking). The defenses are strong password handling, MFA, and token generation, regeneration and expiry.

Correction

Add MFA at minimum. Multi-factor authentication is not mentioned anywhere in the video, as an attack target or as a defense.

#17 8:54–9:09 ∅ Omission Narration

File upload defenses mostly missing

In the video

The video says to validate a file’s actual content, “not just looking at the file extension.”

In the module

The upload is dangerous if the server “stores it in a web-accessible place and executes it.” Four defenses: validate file type and actual content, rename uploaded files, store them outside the web root, and never execute them.

Correction

Add the other three defenses. The knowledge check explanation for question 8 lists all four.

#18 after 9:09 ∅ Omission Not in the video

API weaknesses are missing

In the video

The video moves from file upload to tools. APIs appear only as passing mentions at 1:32 and 2:08.

In the module

Access & Authentication → “File upload and API weaknesses”: APIs are “one of the most critical modern surfaces.” The 2025 Top 10 folds BOLA (broken object-level authorization) and BFLA (broken function-level authorization) into the #1 category. Authenticate and authorize every endpoint, validate every parameter, and never assume a caller is the official client.

Correction

Add a short segment. BOLA and BFLA are never named in the video, and the knowledge check explanation for question 2 uses both terms.

Section 5: Tools 9:10–10:48

#19 9:41–10:01 ∅ Omission Narration

Burp Suite’s components and ZAP’s features not named

In the video

Burp Suite and OWASP ZAP “intercept, pause, modify, and replay HTTP requests.”

In the module

Burp Suite: Proxy intercepts and modifies traffic, Repeater replays and tweaks requests, Intruder fuzzes inputs at scale, Scanner automates detection. OWASP ZAP offers an intercepting proxy, automated scanning and spidering, and suits learning and CI/CD integration.

Correction

Name the four Burp components. Students will meet them in the labs.

#20 10:13–10:46 ∅ Omission Narration and slide

Testing spectrum is thinner than the module’s

In the video

DAST “is what Burp Suite does.” SAST example: SonarQube. SCA: no tool is narrated; the slide shows Snyk.

In the module

Burp and ZAP are DAST tools, good at injection, XSS, misconfiguration and runtime access-control issues. SAST tools: Semgrep, SonarQube, Checkmarx, catching injection and crypto flaws. SCA tools: Snyk and OWASP Dependency-Check. A mature program runs SAST and SCA in the pipeline, DAST against running builds, and manual penetration testing to validate everything in context.

Correction

Say that ZAP is also DAST, and add manual penetration testing as the fourth element. The video also describes supply-chain risk as “climbing up” the Top 10 here, after calling it a new category at 4:21; the module calls it new or expanded.

#21 before 10:48 ∅ Omission Not in the video

Supporting tools not covered

In the video

The tools section ends after SCA.

In the module

Tools → “Supporting tools and practice targets”: Gobuster and dirb for directory brute-forcing, Nikto for server-level checks, and specialized scanners for APIs and frameworks. The deliberately vulnerable apps are DVWA, OWASP Juice Shop and WebGoat.

Correction

Add one sentence on discovery tools. See the first item for the practice targets.

Section 6: Countermeasures and review 10:48–12:21

#22 10:58–11:42 ∅ Omission Narration

One of the four secure-coding principles is absent; shift-left is reduced to threat modeling

In the video

Three principles are covered: validate input on the server, separate code from data, enforce authorization on the server. “Shifting left” is illustrated only by threat modeling during design.

In the module

The fourth principle is robust authentication and sessions: strong password handling, MFA, unpredictable tokens, regeneration after login, expiry and secure cookie flags. Shift left also means SAST in the pipeline at commit, SCA before dependencies ship, and DAST plus manual testing on the running application, because flaws are cheapest to fix early. The module links this to the 2025 list’s Insecure Design and Supply Chain categories.

Correction

Add the fourth principle and connect the SAST, SCA and DAST tools from Section 5 to the lifecycle.

#23 11:17–11:26 ≈ Imprecise Narration

Parameterized queries credited with defeating all injection

In the video

“To defeat injection attacks once and for all, you use parameterized queries.”

In the module

Parameterized queries and prepared statements “pass user data to the database as data, never as executable SQL.” The defense for the whole family is the principle, separate code from data, applied through parameterized queries, safe APIs, output encoding and input validation.

Correction

Parameterized queries stop SQL injection. They do nothing for command injection, which needs safe APIs that avoid the shell, or for XSS, which needs output encoding. The video does give output encoding for XSS in its next sentence.

#24 after 11:42 ∅ Omission Not in the video

The reinforcing layers are missing

In the video

The countermeasures stop at secure coding and go straight to the review.

In the module

Countermeasures → “Reinforcing layers”: a Web Application Firewall that blocks known injection and XSS patterns and provides virtual patching, “a layer, never a substitute for fixing the code”; security response headers (Content-Security-Policy, HSTS, X-Content-Type-Options); comprehensive logging and alerting, the concern of A09; and regular penetration testing and code review.

Correction

Add all four. The video never mentions a WAF, and the knowledge check explanation for question 10 does.

#25 11:51–12:18 ≈ Imprecise Narration

Module’s five ideas reduced to “two fundamental root causes”

In the video

“Almost everything we’ve talked about boils down to two fundamental root causes”: failing to separate code from data, and trusting the client.

In the module

Countermeasures → “The through-line” gives five ideas: don’t trust the client, keep code and data separate, enforce access on the server, handle identity and sessions properly, and build security in throughout the lifecycle. “Every item in the OWASP Top 10 is, at root, a violation of one of these.”

Correction

Present the two causes as the video’s summary of injection and access control only. Authentication and session failures, which the video covered at 8:21, do not fit either one.

Closing thought on AI 12:21–13:13

#26 12:23–13:02 ∅ Omission Narration

AI’s role in testing narrowed to payload generation

In the video

AI “can help us generate test payloads” and “writes vulnerable code at scale,” producing “cryptographic and injection flaws.”

In the module

Tools → “The AI dimension”: CEH v13 emphasizes AI-assisted testing. AI helps generate payloads, triage scanner output and reason about multi-step exploits that scanners miss. AI coding assistants generate injection patterns, authentication weaknesses and cryptographic mistakes. AI is “a powerful accelerant on both sides.”

Correction

Minor. The video’s conclusion matches the module’s: demand for testers rises. Add the two other uses and authentication weaknesses.
